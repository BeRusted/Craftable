# M2 严格实施计划：单步合成与补偿式事务

- 目标版本：Minecraft 1.21.1 / NeoForge 21.1.235
- 前置状态：M1、M1.1 已验收
- 状态：已完成并通过人工验收（2026-09-06）

## 1. 唯一目标

把 M0.2 的“能直接做出一个物品”原型收敛为可信的单步玩家合成事务：一次请求只执行一个已存在的原版有序或无序工作台配方，完整处理输入组件、实际组装结果、配方剩余物、输出容量、资源竞争、失败恢复以及玩家合成事件语义。

M2 不扩大“能做什么”，只保证当前已允许的一步制作“做得正确”。

## 2. 范围预算

### 2.1 必须完成

- 仅 `minecraft` 命名空间、原版 `SHAPED_RECIPE` 与 `SHAPELESS_RECIPE`；
- 2×2 配方使用玩家固有能力，3×3 配方要求环境快照中的工作台能力；
- 最多九个输入，使用 `Ingredient.test` 选择带实际组件的输入栈；
- 构造真实 `CraftingInput`，再次执行 `matches`，并通过 `assemble` 得到结果；
- 在玩家上下文中取得 `getRemainingItems`；
- 输出和所有剩余物必须能完整进入玩家主背包，否则不消耗输入；
- 提交顺序固定为：新快照 → 规划 → 全量复验 → 提取托管 → 插入输出与剩余物 → 标记提交 → 玩家合成回调；
- 事务前后使用精确物品与组件指纹，不把相同物品、不同组件视为同一栈；
- 支持多端点提取、提交中失败恢复、相邻请求争用最后一份材料；
- 尊重 `doLimitedCrafting` 与玩家配方解锁状态；
- 触发物品 `onCraftedBy`、NeoForge `ItemCraftedEvent`、配方进度判据和正常配方解锁语义；
- 单元测试、故障注入测试、GameTest、客户端/专用服务器启动与人工复测清单。

### 2.2 明确不做

- 递归规划、中间产物或“部分完成”（M4）；
- 熔炉、高炉、烟熏炉和时间压缩（M5）；
- 批量制作、最大制作数量；
- 撤销历史（M7）；
- 特殊/动态配方、第三方配方序列化器或第三方容器能力；
- 掉落物、实体库存、村民交易或生物互动；
- M3 的配方书集合、三态渲染和实体 3×3 菜单修复；
- 数据库式锁、跨 tick 事务或提前设计公共事务 SPI。

任何实现需要上述能力时，M2 返回结构化“不支持”，不得顺手建立未来框架。

## 3. 依赖方向与类预算

```text
network
  -> DirectCraftingService（唯一公开门面）
       -> DirectCraftingPlanner（纯读取、无世界写入）
       -> DirectCraftingTransaction（复验、托管、提交、补偿）
            -> MainInventoryInsertion（背包容量模拟与精确插入）
       -> M1 EnvironmentSnapshot
```

保留 `DirectCraftingPlan` 和 `DirectCraftingEvaluation` 作为不可变值对象。M2 最多新增上述三个包私有实现类和一组 GameTest，不创建 `compat`、通用动作系统、事务总线或抽象工作站层。

## 4. 事务状态机

```text
PLANNED
  -> REVALIDATED
  -> ESCROWED
  -> INSERTED
  -> COMMITTED
  -> NOTIFIED

任一 COMMITTED 之前的失败 -> RESTORED
COMMITTED 之后的通知回调失败 -> 保持 COMMITTED，仅记录错误
```

### 4.1 PLANNED

- 规划只读取同一份新鲜环境快照；
- 输入分配使用“候选最少优先”的有界回溯，避免重叠标签材料被贪心错误占用；
- 计划保存完整 2×2/3×3 事件网格、每个来源槽位的精确栈指纹、实际输出和剩余物副本；
- 所有集合防御性复制。

### 4.2 REVALIDATED

- 仍在服务端主线程、同一玩家上下文和同一背包菜单；
- 所有端点仍有效；
- 每个来源槽位的物品、数量和数据组件与计划指纹完全相同；
- 重新模拟玩家背包在扣除玩家来源输入后容纳输出与剩余物；
- 所有检查完成前不提取第一件物品。

### 4.3 ESCROWED / INSERTED

- 按快照端点顺序和槽位顺序提取；
- 每次提取的返回栈进入局部托管列表，并核对数量与组件；
- 输出先插入玩家主背包，再插入配方剩余物；
- 正常成功路径不向世界掉落物品；
- 插入发生任何异常或与模拟不一致时，使用提交前备份恢复玩家背包与受影响来源槽。

### 4.4 COMMITTED / NOTIFIED

- 仅在所有物品变更完成后调用 `setChanged` 和菜单同步；
- 普通玩家合成不调用自动合成方块专用的 `onCraftedBySystem`；
- 提交后依次触发玩家物品制作回调、NeoForge 制作事件、配方判据和配方解锁；
- 这些通知型回调的异常被记录但不回滚已提交物品，避免事件监听器撕裂事务。

## 5. 核心不变量

1. 预览永不写世界；
2. 客户端不能指定输入槽、数量、输出或剩余物；
3. 每个成功事务满足“输入变化 + 输出 + 剩余物”的配方守恒；
4. COMMITTED 前失败时，玩家背包和所有已接触来源槽恢复为提交前状态；
5. 容量不足时不提取任何输入；
6. 相邻两个请求不能消费同一份最后材料两次；
7. 组件不同的物品不合并，也不能通过复验；
8. 所有世界访问仍在服务端主线程；
9. 无 JEI、无客户端界面也能通过服务端事务测试；
10. 不支持的配方明确拒绝，不退化为猜测执行。

## 6. 测试矩阵

### 6.1 纯逻辑与故障注入测试

- 防御性复制与非法计划拒绝；
- 重叠 Ingredient 的非贪心分配；
- 同物品不同组件不合并；
- 多输出栈联合容量模拟；
- 提取后腾出的玩家槽参与容量计算；
- 中途提取失败恢复先前槽；
- 精确栈指纹变化导致复验拒绝。

### 6.2 GameTest

- 箱中材料完成一次 2×2 原版配方；
- 箱子 + 工作台完成 3×3 且返回桶等剩余物；
- 满背包时箱内输入保持不变；
- 两次相邻执行争用最后一份材料，恰好一次成功；
- 统计、配方判据与 NeoForge `ItemCraftedEvent` 至少各有一次实际证据。

### 6.3 运行时基线

- `test`、`gameTestServer`、`build`；
- 专用服务器进入 `Done`，无客户端类泄漏；
- 客户端进入主菜单，网络协议与反馈类正常装载。

## 8. 首轮人工复测后的定向修复（2026-09-06）

玩家在 A 项发现：木棍按钮会按原版 30 tick 周期在木板配方与竹子配方之间轮播；旧实现直接读取当帧 `RecipeButton#getRecipe()`，因此绿框与 `C` 键会随着不可制作的竹子配方一起失效。

修复严格限制在现有按钮适配层：

- 从按钮的 `RecipeCollection` 取得当前展示集合中的候选配方；
- 状态按 `CRAFTABLE > PARTIAL > BLOCKED` 聚合，不把动画当前帧当成唯一状态；
- `C` 优先选择服务端已确认可制作的候选，原版本地可制作状态仅作尚未收到预览时的回退；
- 每四个客户端 tick 最多请求一个陈旧候选，保持与服务端既有限流一致，不新增批量协议；
- 用纯逻辑回归测试固定“当前轮播项不可制作，但同按钮另一配方可制作”这一行为。

该修复不建立全配方目录、不改变 `showing craftable` 的原版集合，也不提前实现 M3。随后进行的定向复测全部通过，M2 正式关闭。
