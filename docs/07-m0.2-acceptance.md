# M0.2 验收报告

- 验收日期：2026-09-02
- 环境：Minecraft 1.21.1 / NeoForge 21.1.235 / 纯原版资源与工作站
- 结论：**技术原型有条件通过，玩家功能版本不通过**

M0.2 的目标是验证高风险假设，而不是交付可发布版本。实机测试证明原版配方书能够作为 Craftable 的主要入口，也证明附近容器中的材料可以由服务端安全用于一次直接合成；同时暴露了三个必须改变正式设计的客户端边界。因此关闭 M0.2，问题转入 M3 的强制验收条件，不继续在原型层叠补丁。

## 1. 验收结果

| 项目 | 实际结果 | 判定 |
|---|---|---|
| 玩家背包内有材料、附近有工作台 | 钻石镐被原版配方书视为可合成，`showing craftable` 正常，`C` 可制作 | 通过 |
| 附近容器内有材料、附近有工作台 | `C` 可制作，但原版仍保留不可合成状态；Craftable 绿框叠加在原版红框外，`showing craftable` 会过滤掉该配方 | 不通过，已定位 |
| 不依赖原版解锁显示完整配方目录 | 当前注入没有在配方集合初始化后稳定建立独立可见集合，未解锁/未进入 `known` 的配方仍可能不显示 | 不通过，已定位 |
| 左键点击 3×3 配方预览 | 配方书按 3×3 判断，但真实 `InventoryMenu` 仍为 2×2，虚影位置和槽位映射异常 | 不通过，已定位 |

| 服务端权威执行 | 显示状态异常时仍由服务端重扫并正确完成制作 | 通过 |

## 2. 根因

### 2.1 配方集合与附加描边是两套状态

原版 `RecipeCollection.canCraft` 使用 `RecipeBookComponent` 内由玩家背包和合成槽填充的 `StackedContents`，结果写入原版 `craftable` 集合。`showing craftable` 调用 `hasCraftable()` 过滤集合，按钮也以 `isCraftable()` 选择原版视觉。

M0.2 只在玩家悬停后取得服务端状态，并在 `RecipeButton` 渲染末尾额外画框。这个状态没有进入原版集合，所以出现“原版不可合成 + Craftable 可合成”并存，过滤仍以原版结果为准。正式实现必须只有一个面向玩家的状态源。

### 2.2 配方目录不等于玩家解锁记录

客户端配方管理器已经接收服务端同步的完整配方目录，`ClientRecipeBook` 再把它们分类为集合；但每个集合的 `known` 仍随玩家原版配方书解锁记录更新。M0.2 在 `updateKnownRecipes` 内绕过一次 `RecipeBook.contains`，没有解决集合创建与解锁更新的生命周期差异。

正式实现不“主动解锁所有配方”。它从客户端已同步目录维护 Craftable 独立显示集合，并让 `ALL/UNLOCKED_ONLY` 仅决定显示策略，绝不修改玩家配方进度、提示或成就。

### 2.3 有效 3×3 与真实 2×2 拓扑不一致

M0.2 只把 `RecipeCollection.canCraft` 的宽高参数改成 3×3。左键预览和原版放置仍调用真实菜单的 `getGridWidth()`、`getGridHeight()`、槽位列表和结果槽，因此三行配方不可能正确映射到四个输入槽。

正式实现必须选择完整方案：附近工作台存在时，客户端与服务端使用同一实体 3×3 菜单拓扑；工作台不可用时回到 2×2。菜单变化需要明确的世代与重开策略，不能只改显示。

## 3. `InventoryCrafting` 参考实现评估

本地参考源码 `InventoryCrafting-trunk-1.21.1.zip` 证明 1.21.1 中可以构建 3×3 玩家背包：它重建 `InventoryMenu`、输入槽、结果槽和背包屏幕，并在客户端与服务端安装自定义菜单。

它也展示了直接照搬的高风险面：

- 替换 `Player.inventory` 和 `Player.inventoryMenu`，扩大与存档、重生、游戏模式及其他背包修改的冲突面；
- 全面改变槽位编号，必须同步重写 Shift 点击、护甲、副手、创造模式与配方转移逻辑；
- 以捕获并忽略异常、越界 `getSlot` 返回 `null` 等方式掩盖拓扑不同步；
- 通过 Access Transformer 放宽多个原版字段，版本升级和组合模组风险较高。

Craftable 只采纳“实体 3×3 在技术上可行”这一结论，不复制代码或补丁策略。我们的实现不得替换玩家库存对象，不得吞掉菜单异常，并必须以槽位不变量和生命周期测试为入口。

## 4. 后续强制要求

M3 完成前必须同时满足：

1. 环境权威三态进入配方集合，按钮、过滤、提示和 `C` 结果一致；
2. `ALL` 可显示客户端目录中的受支持配方而不修改原版解锁进度；
3. 附近工作台时存在真实且同构的 3×3 背包菜单，左键虚影和配方放置无错位；
4. 状态按可见页或环境世代批量刷新，避免“只有悬停后才变色”和请求风暴；
5. 对工作台移除、移动出范围、死亡、重生、切维度、切换游戏模式、断线重连和专用服务器分别测试。

M0.2 代码保留为实验依据；在 M3 正式实现到位前，不把当前额外描边或伪 3×3 行为视为产品功能。
