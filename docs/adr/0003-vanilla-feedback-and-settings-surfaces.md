# ADR-0003：原版式反馈与设置入口

- 状态：已接受
- 日期：2026-09-03

## 背景

Craftable 的交互应让人感觉是原版能力的自然补全。M0/M1 原型把制作结果写入动作栏，虽能证明网络闭环，但它没有区分“正常成功”“可立即修正的失败”“需要阅读的计划”和“管理员诊断”。配置也已经通过 `ModConfigSpec` 持久化，却尚未为玩家提供游戏内入口。

此外，检测范围、检测算法、掉落物、实体动作和时间压缩都会改变世界规则。在单人游戏中客户端与服务端同处一个进程，不能因此把这些规则降格为客户端偏好；否则同一界面在多人游戏中会产生错误的权限暗示。

## 决策

### 1. 按语义选择原版界面

Craftable 不实现常驻自定义 HUD，也不自行绘制固定坐标通知。所有反馈通过一个客户端反馈路由器进入既有原版界面：

| 信息 | 原版界面 | 规则 |
|---|---|---|
| 正常制作成功 | 物品进入背包、原版音效/动画 | 默认不弹文字；连续制作不得刷屏 |
| 玩家主动执行失败 | 右上角 `SystemToast` | 标题简短、原因一行；连续失败更新同一个 Toast |
| 配方当前状态与短缺 | 配方按钮样式和 Tooltip | 不在未操作时主动弹窗 |
| 多步计划、部分完成确认 | 配方书内的原版风格面板/确认界面 | 允许阅读、键盘操作和旁白 |
| 调试命令 | 聊天命令输出 | 保持可复制；不混入普通玩家通知 |

失败 Toast 的内容来自服务端结构化结果，客户端只决定详细或简略显示。任何客户端文案都不能把失败改写为成功。

### 2. 只维护一套配置真值和一套配置界面

- 配置继续由 `ModConfigSpec` 定义、校验和持久化；
- 使用 NeoForge 1.21.1 自带的 `ConfigurationScreen` 生成原版 `OptionsSubScreen` 风格页面，不复制滑块、开关、撤销和默认值逻辑；
- 基础入口为“模组 → Craftable → 配置”；M3 再评估通过公开屏幕事件在原版“选项”页增加一个直达按钮，仍打开同一个页面；
- 不把扫描、自动交易或时间压缩等玩法规则直接塞入“辅助功能”。辅助功能页未来最多提供显示、颜色、旁白和通知偏好的入口；
- 单人游戏可编辑本地世界的服务端配置；连接远程服务器时只允许编辑客户端偏好，世界规则只读且以服务端有效值为准；
- 尚未实现的能力不注册“死开关”，在对应里程碑落地时才出现。

### 3. 设置归属

| 设置 | 归属 | 落地里程碑 |
|---|---|---|
| 水平/垂直检测范围 | SERVER | M1 已实现，M1.1 接入游戏内配置页 |
| 配方书增强、失败详情、通知/旁白偏好 | CLIENT | M1/M3/M6 |
| `BOX/EUCLIDEAN/LINE_OF_SIGHT/REACHABLE` 检测模式 | SERVER | M9 |
| 是否使用掉落物和实体库存 | SERVER | M9 |
| 是否允许村民交易、生物互动及各动作子开关 | SERVER | M10 |
| 是否允许无等待处理与批量上限 | SERVER | M5 |

“生物行为”不只用一个过宽布尔值表达：提供总开关时，还必须为村民交易、剪羊等有不同副作用的动作提供独立策略。默认只开放经过明确实现和测试的白名单动作。

## 架构约束

- UI 不直接读写执行服务的内部状态；
- 客户端配置不能改变资源、成本、权限或时间结算；
- 多人客户端本地的服务端配置文件不是服务器真值，M3 的界面必须使用服务端同步的有效规则摘要；
- 增加“选项”或“辅助功能”入口时优先使用 NeoForge 公开 `ScreenEvent`，只有公开事件不足才允许窄 Mixin；
- Toast 必须合并重复消息，并遵守原版通知显示时长和无障碍设置；
- 新设置必须同时具有范围、默认值、翻译、Tooltip、所有权和即时生效/重启说明。

## 后果

- 当前失败提示更接近原版，且不会占据动作栏；
- 配置页面复用 NeoForge 维护的原版风格控件，降低 UI 代码量；
- 完整的“选项”直达入口和服务端规则摘要需要 M3 的同步模型，不能只靠客户端读取本地 TOML；
- 高级环境与实体动作仍按原路线实现，不会因为先出现开关而形成空壳功能。
