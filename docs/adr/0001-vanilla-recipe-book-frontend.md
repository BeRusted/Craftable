# ADR-0001：使用原版配方书作为默认前端

- 状态：已接受
- 日期：2026-09-01
- 适用版本：Minecraft 1.21.1 / NeoForge 21.1.235

## 背景

Craftable 的定位是基础能力增强，而不是增加独立玩法体系。自行开发 JEI 风格配方浏览器会重复实现搜索、分类、分页、物品图标、提示和无障碍行为，也会让体验更像额外模组系统，而不是“游戏本来就应该这样”。

原版背包和工作站界面已经使用 `RecipeBookComponent`。NeoForge 1.21.1 提供配方书分类注册、屏幕事件和 Access Transformer 等扩展手段，但没有一个可以完整替换材料来源、有效网格、可合成判定和点击行为的统一 API。

## 决策

1. 原版配方书是 Craftable 在未安装配方查看模组时的默认且主要前端。
2. Craftable 不开发独立的 JEI 风格主浏览器。
3. 第一阶段复用原版配方书的搜索、分类、分页、图标、提示和叙述，并增加：
   - 附近工作台带来的有效 3×3 配方上下文；
   - 可合成、部分可合成、不可合成三态；
   - `C` 制作和统一计划/缺口提示。
4. JEI 是并存的可选前端。JEI 存在时，原版配方书增强继续保留；JEI 接入同一目标、状态、预览、`C` 制作和第二阶段 `Z` 撤销能力。
5. 第二阶段把更多第三方配方、村民交易、生物动作和工作站 UI 接入原版配方书或与其一致的原版风格界面。
6. 两个前端只表达玩家意图和展示服务端结果。环境发现、规划、资源消耗、产出和撤销始终由服务端权威实现。

## 实现约束

- 优先使用 NeoForge 公开的配方书注册与 `ScreenEvent`；
- 对原版私有状态只使用窄范围 Access Transformer 或 accessor Mixin；
- 不复制整份 `InventoryScreen`、`RecipeBookComponent` 或 JEI 内部 GUI；
- 不通过批量解锁配方改变玩家进度，显示范围由独立策略控制；
- 三态预览按环境世代缓存，只计算可见条目和悬停目标；
- 原版配方书与 JEI 必须共享同一 `CraftingFrontendBridge` 和状态模型。

## 结果

正面结果：

- 纯原版环境中的体验更一致；
- 第一阶段不需要维护一套完整配方浏览 UI；
- 搜索、分类、提示、键鼠和无障碍能力可以复用；
- JEI 兼容不会成为另一套执行逻辑。

代价与风险：

- 原版配方书内部成员并非全部公开，版本升级时需要回归窄范围注入；
- 原版配方书不能自然表示所有机器、交易和世界交互，第二阶段仍需显示适配器；
- 大量可见配方的状态计算必须缓存和限流；
- JEI 是否能通过公共 API 完整承载三态覆盖，需要在阶段 0 原型中验证。

## 被否决的方案

- **独立 JEI 风格浏览器**：重复工作多，偏离原版体验，且与 JEI 同时存在时容易形成两个竞争入口。
- **安装 JEI 后关闭原版增强**：导致同一模组在不同客户端出现两套语义，也违背原版配方书始终可用的产品决策。
- **批量解锁所有原版配方**：会污染配方发现、进度与提示状态，不能作为显示全部目标的实现手段。
