# ADR-0004：M2 使用主线程补偿式单步事务

- 状态：已接受
- 日期：2026-09-03

## 背景

Minecraft 的多个 `Container` 之间没有数据库事务、统一版本号或跨库存锁。M0.2 通过复制玩家背包和受影响槽位实现了原型回滚，但尚未形成实际输入网格、剩余物和标准玩家合成回调的完整契约。

## 决策

M2 只对 M1 已支持的原版容器，在服务端主线程内执行一次补偿式事务：

1. 使用新鲜环境快照规划一次配方；
2. 在任何写入前精确复验全部来源与输出容量；
3. 复制玩家主背包和受影响来源槽作为提交前像；
4. 按稳定顺序把输入移入局部托管；
5. 完整插入输出和剩余物后提交；
6. 提交前失败恢复提交前像；
7. 提交后再触发不能安全回滚的统计、进度和 NeoForge 通知事件。

计划保存的是物品副本和稳定端点引用，而不是客户端给出的成本。预览计划不被执行路径复用，创建请求始终重新扫描和重新规划。

## 为什么不模拟一个隐藏工作台菜单

隐藏菜单会引入槽位拓扑、菜单生命周期、客户端同步和 M3 实体 3×3 界面的耦合。M2 改为直接构造 `CraftingInput`，但用 `SimpleContainer` 的输入副本向 NeoForge `ItemCraftedEvent` 提供与手工制作等价的观察内容。

## 为什么提交后事件失败不回滚

事件监听器可能已经修改统计、进度或其他世界状态，无法证明这些副作用可逆。物品提交完成后若监听器抛出异常，回滚物品反而可能制造复制或不一致。因此 M2 记录错误并保持事务成功；事件前的任何失败仍必须恢复物品状态。

## 后果与边界

- 对当前原版容器可以提供确定的逐槽恢复；
- 两个网络请求在主线程串行执行，第二个请求会看到第一个提交后的新快照；
- 第三方 `IItemHandler`、会在提取回调中改变世界的端点和跨 tick 工作站必须另行声明补偿能力，不能自动继承本 ADR 的保证；
- M7 的玩家撤销与本 ADR 的故障补偿是两件事，不能复用同一个“无条件回滚”入口。
