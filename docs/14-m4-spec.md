# M4 行为规格：有界递归、数量与安全部分完成

- 日期：2026-09-08。
- 状态：09-17 第五批已接入本地详情/候选/MAX，沿用协议 7；实际确认仍由服务端新鲜审阅和原事务处理。M4.8 完整性能门禁及 M4.9 尚未完成，证据见 [实施进展](17-m4-progress.md)，人工验收尚未完成。
- 交互补充：[16-m4-interaction-and-performance.md](16-m4-interaction-and-performance.md) 细化余料掉落、双击 C、可编辑物品链、滑槽/MAX 与集中效率阶段。
- 前置：M0–M3 已验收；历史 M4/M4.7 为协议 6，当前浏览迁移交付为协议 7，不能混用旧 JAR。
- 本文是 M4 的具体契约；与早期产品草案冲突时以本文及 ADR-0006 为准。实施顺序见 [15-m4-implementation-plan.md](15-m4-implementation-plan.md)。

## 1. 唯一目标与范围

让现有原版配方书 C 入口能够把“当前已有资源 → 多步普通合成 → 请求目标”作为一次安全操作；确实无法完成时，只执行数量有界、能解释用途的部分计划。

纳入：原版普通有序/无序配方、多层依赖、标签候选与回溯、常见存储转换、批次数量、剩余物、缺口、部分完成、原版风格计划详情及确认。

不纳入：炉类和燃料（M5）、Z 撤销、JEI、第三方适配器、数据包配方通用支持、实体行为、掉落物作为输入、可达性、新工作站 GUI、玩家保留物品管理系统、持久任务队列、后台持续合成。检测范围、模式边界、实体菜单和普通左键行为沿用 M3。可配置的余料溢出实体输出及物品链展示纳入本阶段，但不建设新工作站 GUI。

不自动制作并放置缺失工作台，也不把箱中工作台物品当作已存在的工作站。身上有铁矿并不代表 M4 可以取得铁锭；熔炼路径尚未支持，不应展示为已可制作。

## 2. 目标和数量：不破坏 C 的原有习惯

### 2.1 根目标

目标是 `根配方 ID + 数量模式 + 完整/部分意图 + 节点配方约束 + 余料策略`，不是“背包里最终拥有多少件物品”。已有钻石镐不抵扣新请求的一次钻石镐制作；已有木棍可以抵扣中间需求。

根配方固定，不在服务端悄悄换成另一条输出相似的配方。配方书同一按钮的多配方候选仍由 M3 的统一状态选择规则处理，与轮播帧无关；内部依赖可以搜索不同受支持配方。若根 ID 无效或不支持，应明确拒绝。

### 2.2 批次不是物品数

| 操作 | 请求语义 | 示例 |
|---|---|---|
| 单击 C | 只尝试完整执行 1 次，失败不消费 | 木棍得到 4 根，钻石镐得到 1 把 |
| 双击 C | 前一同目标完整尝试失败后，显式请求有界部分完成 | 缺钻石时准备木棍；不是制作 MAX |
| Shift+C | 打开可编辑物品链页，不立即消耗 | 工作站图标、路线选择、数量滑槽与独立合成按钮 |
| 详情中的固定数量 | 执行 N 次根配方 | 木棍 3 次得到 12 根；同时显示次数和件数 |
| 详情中的 MAX | 在服务端上限内寻找最多可完成根批次 | 显示已找到数量与是否达到上限，不声称无限最大值 |

新快捷操作必须遵守搜索框焦点：输入 C/Shift+C 时不制作、不打开详情；保留原版普通左键及 Shift 左键配方放置。

任何输入、输出、剩余物均按完整配方批次结算。不把两块木板→四根木棍切成一块木板→两根木棍。需求向上取整产生的余量归玩家，不隐藏或销毁。

固定 N 的结果：完成 N 次为完整成功；能完成 1..N-1 次为部分目标完成；零次但有安全中间步骤为材料准备；两者均没有则无进展。只有显式双击/详情“尽可能合成”意图允许提交部分计划，普通 C 和详情“合成”不能在失败时自行降级。MAX 只寻找可完成目标，不为尚未完成的额外批次准备中间件。

MAX 不假设数量与输出容量严格单调，不能未经证明用二分查找。若预算内只找到可行下界，详情标为“至少可制作 K 次，搜索未完成”，不能标“最大 K”；必须改成已确认固定 K 再执行。

## 3. 材料和配方的合法性

### 3.1 与现有实现一致的支持白名单

每个节点均须通过支持判定，而非只检查根节点：

- `minecraft` 命名空间、普通 shaped/shapeless serializer、非 special、非 incomplete，且能构造并校验实际 CraftingInput；
- 使用真实 Ingredient 匹配、`matches`、`assemble` 和 `getRemainingItems`；不得用输出图标或简单物品 ID 代替语义；
- 普通配方的被动候选输出用于索引，实际输出/组件仍须用具体输入验证；发生不一致或发现自定义行为时保守拒绝；
- 所需 2×2/3×3 能力已存在，当前 stillValid 的实体工作台仍可提供 3×3；
- `doLimitedCrafting=true` 时所有依赖配方在请求开始即已解锁。M4 不模拟“先做一步触发解锁后再做下一步”；提示先手工解锁依赖，以免在只读搜索里猜测进度事件。

2026-09-13 诊断修订：未解锁的**无材料起点备选配方**不等于当前目标未解锁。可达性预筛须检查该候选自身所有输入，不只检查同种产物是否可由另一配方获得。放宽的存在性闭包不检查权限，只用于排除无起点路线；实际展开与执行仍逐配方检查权限。一个原木准备木镐时缺口归属木板，不转述为没有选用的竹子路线。

命名空间不是可信证明。数据包覆盖原版 ID 的情况仍须经过上述实际输入/输出验证和预算限制；没有安全语义就不自动支持。

### 3.2 资源边界和保护

- 复用 M1 有序端点、锁/区块/可用性规则。主背包 0..35 参与；护甲、副手、鼠标栈及两个菜单中的手动合成网格不参与自动取材。
- M4 不挪动、返还或清空玩家正在手工摆放的网格，也不把网格当作额外存储。
- 默认排除相对该物品默认栈具有非默认组件的材料，例如命名、附魔、损伤等，包含直接和递归路径。完整保留物品清单后移；本阶段不增加“强制吃掉保护材料”快捷键。
- 在合法材料中保留端点顺序与稳定槽位顺序。已有中间物优先于新制造，但该偏好可回溯：不能先吃掉一个通用材料而阻塞后面的精确需求。
- 所有数量计算检查溢出，精确栈键包括组件；存量不能在多个分支或多个目标批次间重复承诺。

此保护规则比 M2 更保守，是明确的安全调整；有命名材料却拒绝自动消费时，提示“材料受保护”，不是无解释的材料不足。只依据有权访问的端点诊断，不扫描被锁容器来证明“里面其实有材料”。

## 4. 规划算法：先可靠，再优化

### 4.1 采用有界需求回溯，不建设通用机器框架

M4 使用确定排序的需求驱动回溯与局部资源账本，优先返回第一条经完整验证的可行路径。暂不实现通用超图最佳优先搜索、强连通分量求解器或全局成本优化。

基本流程：

1. 取得只读资源副本、工作站能力、配方世代及规则；索引只查可能产出所需材料的配方。
2. 对需求优先匹配可用现物，按候选约束数量先处理更窄的条件。
3. 对缺口枚举产物可匹配 Ingredient 的候选配方，展开完整批次；每个候选分支拥有可回退账本。
4. 构造实际输入，验证配方并加入实际剩余物；满足其他需求时可复用这些余量，不能把同一空桶或木棍计数两次。
5. 执行顺序模拟成功后输出有序步骤及净提取/交付；失败回溯到其他材料/配方。

输出用“有序步骤列表 + 引用已产生资源的关系”即可，不同时维护一套树、一套 DAG 和一套动作虚拟机。一个步骤对应一次真实配方调用；展示层可合并相邻同配方步骤，执行层不能乘法跳过剩余物和回调。

候选排序：现物优先 → 可证明的原版低损失存储转换 → 较少预计动作 → 已有端点顺序 → 稳定配方 ID。完整可行计划优先于任何部分计划；排序不是全局最优证明，也不引入“物品稀有度”魔法分数。

### 4.2 循环和缓存

- 访问状态必须包含需求数量、已保留/可用资源及规则上下文；只按物品 ID 的全局 visited 会误杀合法铁粒→铁锭。
- 同一分支回到无净进展的等价需求/账本状态时剪枝；无初始资源的铁锭↔铁粒不能启动。
- 有初始铁粒时允许按真实批次转换；不得仅因图中存在双向边而把两条配方全部禁用。
- 不自动利用闭环收益；M4 对需要重复穿越同一活动转换环才能成功的路径保守拒绝并解释搜索限制。没有普遍可靠的“跨不同物品总数守恒”判断，不能以 1 铁锭→9 铁粒数量增加为作弊判据。
- 记忆化仅限一次请求且有容量界限；完整状态相同才复用已证明不可行的结果。预算截断不能缓存成永久无解。
- 索引按配方/标签重载世代失效。预览不缓存可直接提交的活计划，不跨玩家复用带库存的搜索结果。

M4.7 增补：允许原索引持有共享的规范化需求/生产候选关系，并将有界、完整的知识项保存到当前存档，语义指纹匹配后跨重启复用。上述“一次请求记忆化”指带资源的搜索状态，不限制纯配方知识；上述重载失效仍作用于运行时句柄与所有授权。永久空结果只允许表示完整计算的无生产关系，不能表示某次缺料或超时。详见 [知识契约](19-m4-recipe-knowledge.md) 和 ADR-0007；实际求解/剩余物/事务语义不变。

## 5. 部分完成：有用、有限、再次点击不重复准备

### 5.1 分类和安全门槛

部分完成有两类，详情必须区分：

1. **部分目标完成**：固定请求 N，已证明最多能做 K（0<K<N）；交付 K 次实际目标。
2. **准备材料**：无法再完成根目标，但可为剩余请求准备有用中间物。

只有缺少可取得材料导致的已确认阻断，才进入自动材料准备。根工作站缺失、任一步权限/解锁拒绝、未知动态配方、容量不足、搜索未穷尽或预算超限时，不自动执行中间步骤；详情可以解释，但本次世界不变。某条候选分支不合法不代表全局失败，先尝试其余合法候选。

“有用前沿”指当前选定目标路径上、能以已有资源实际到达的最靠近目标的中间需求，不要求跨所有路径的数学最大值。步骤必须同时满足：

- 在目标依赖路径上；先预留现有中间物，再补剩余缺口；
- 仅执行覆盖需求所需的最少完整批次，超出需求部分只允许是配方不可分的余量；
- 最终有新的目标或中间材料被交付，不能仅在托管账本中来回转换；
- 不消耗受保护材料，配方步骤不含生物/经验等世界副作用；显式允许的余料溢出交付按第 6 节处理，掉落风险须提示；
- 普通木材加工和已验证的原版存储转换可作为初始 EXPLICIT_SAFE 白名单；复杂剩余物配方的部分准备必须确认，不因“是普通配方”就自动归为安全；
- 先完成能完成的根批次；随后若准备剩余请求，重新计算未满足需求，不能把已用于成品的原料又计入中间缺口。

重复同一单次 C 时，如果上次准备的木棍仍可访问且已覆盖该单次目标需求，不再制造木棍。玩家移走/使用了中间物后，可再次准备；这是基于现有资源的去重，不是长期记住“上次任务”，不引入持久任务/资源状态。M4.7 的静态知识缓存不参与该去重授权。

### 5.2 默认策略与确认

按玩家反馈，撤销单击失败自动准备的 AUTO_SAFE 草案。默认 `EXPLICIT_SAFE`，双击关联规则见交互补充；只有先表达部分意图，才适用下列策略：

- `NEVER`：固定数量不能全部完成时不修改世界。
- `CONFIRM`：部分计划先打开详情，明确显示“最终目标未完成/只完成 K 次”，再次确认才提交。
- `EXPLICIT_SAFE`：显式双击或详情“尽可能合成”可执行已证明安全的部分计划；不在安全白名单的有用计划退到确认，不自动提交。

服务端允许等级与客户端偏好取更严格者：NEVER < CONFIRM < EXPLICIT_SAFE。客户端不能放宽服务器。MAX 数量始终由详情确认，不绑定无预览的一键大量消耗。

### 5.3 固定基准示例

| 输入环境（主背包有足够空间） | 请求 | 应得结果 |
|---|---|---|
| 工作台；1 橡木原木、3 钻石 | 钻石镐 1 次 | 1 钻石镐 + 2 木板 + 2 木棍；消耗 1 原木、3 钻石 |
| 工作台；1 原木、0 钻石 | 钻石镐 1 次，双击 C / EXPLICIT_SAFE | 4 木棍 + 2 木板；提示仍缺 3 钻石，不截成 2 木棍 |
| 同上，但有 2 钻石 | 钻石镐 1 次，显式部分请求 | 准备同样木材产物；2 钻石不动，缺口为 1 钻石 |
| 上次的 4 木棍仍在，另有很多原木，无钻石 | 再次双击 C | 无新增制作，无原木消耗，仍提示缺钻石 |
| 无工作台；原木、钻石齐全 | 钻石镐 1 次 | 缺少 3×3 工作站，零消耗、零准备 |
| 工作台；27 铁粒、2 木棍 | 铁镐 1 次 | 通过铁粒→铁锭→铁镐完成；没有铁粒则转换环不能凭空启动 |
| 工作台、熔炉；铁矿、煤、原木 | 铁镐 1 次 | M4 不执行熔炼；不将其标为完整可制作，说明缺铁锭/尚不支持炉处理 |
| 工作台；2 原木、3 钻石 | 详情显式尽可能合成 2 次，EXPLICIT_SAFE | 做 1 把；剩余需求已由余下 2 木棍覆盖，交付 2 木板、2 木棍，另 1 原木不动 |

## 6. 容量和单次事务

### 6.1 最终交付容量与余料策略

- 默认 REQUIRE_SPACE：消耗输入后，主背包须装下主产物与所有余料。
- 可配置 DROP_OVERFLOW：主产物必须能装下；余料先入背包，仅溢出部分按原版主动丢弃表现生成实体。部分计划的前沿产物是主产物，不能丢掉后称准备成功。
- 原稿逐步要求中间产物占真实 36 格的限制撤销；只在本次有界同步事务内托管后续仍需消费的中间资源，最终全部结清。公开承认这压缩了临时搬运空间，不承诺逐步手动槽位等价。
- 玩家手动网格、光标、装备与副手不参与自动取材/输出，不生成可跨请求访问的虚拟仓库。
- 容量模拟按最终净提取后的主背包计算；中间账本仍限制栈数/数量/步骤数，丢弃计划限制新实体数。开启配置不是无限丢物或绕过批次/内存预算。
- 具体主产物分类、设置所有权、风险说明和实体失败恢复以交互补充第 1 节为准。

### 6.2 整链提交

禁止用 `for (...) createOne(...)` 拼出递归：这会让中途失败留下已消费的半条链。单步和递归必须经过同一个事务边界，步骤计划长度为 1 就是现有单步。

执行顺序：新鲜扫描 → 整链规划与容量模拟 → 复验游戏模式/菜单/世代/工作站/精确来源 → 备份主背包及所有受影响外部槽 → 一次托管提取 → 插入主产物与可容纳余料 → 创建并核验溢出实体（仅允许时）→ 标记提交 → 按拓扑顺序逐步通知。

中间产物只在本事务内部生成与消耗；净交付包括目标、未消费中间物及所有剩余物。最终插入失败或提取失败则整个请求恢复提交前像；发生实体创建失败时还须先清理本次可安全恢复的精确实体，验证门禁见交互补充，不能只返还库存，不能把技术失败伪装为产品的“部分完成”。后者是提交前明确选定、整体成功的有限计划。

每个实际步骤保留输入副本、真实产物和剩余物以触发原版统计/配方判据/合成事件，包含已被下游消耗的中间物。通知在全部物品提交后执行；隔离各步骤的监听器异常并继续剩余通知，绝不因此返还材料或自动重试已提交事务。M4 不承诺第三方事件监听器看到逐步骤真实背包变化；只保证纯原版路径和明确的提交后观察语义。

## 7. 展示、诊断和网络

### 7.1 同一个状态来源

- `CRAFTABLE`：当前证据可完整执行目标。
- `PARTIAL`：当前有可执行的部分目标/材料准备计划，Tooltip 明确交付内容及确认要求。
- `BLOCKED`：当前没有可执行进展，或受安全/支持边界拒绝。
- 未查/等待刷新仍为独立生命周期 `?`/`~`；搜索预算不足显示“无法确认：搜索达到上限”，不显示虚假的“材料不足”，不自动落成 PARTIAL。

同按钮候选取完整可制作 > 部分可制作 > 不可制作，未知保持独立。原版“仅可合成”只纳入确能交付该按钮最终目标的候选，不把“只能准备木棍”的钻石镐放进该筛选；PARTIAL 在全部目录可见并有独立文字/角标。固定多批次的部分目标进度仅在详情中显示，不污染默认一次的按钮缓存。

部分成功使用原版通知简短报告“已准备 4 木棍；仍缺 3 钻石”，不说“钻石镐制作成功”。完整单次成功且无溢出仍静默。详细计划升级为现有菜单内的可编辑物品链页：目标在右、依赖向左，左上角工作站状态，下方数量滑槽和完整/部分按钮。无法完成也显示受支持的解释路线与缺口，不能伪造不存在的可执行链。原菜单和槽同步仍存活，不另开服务器菜单；Esc 先关详情，第二次才退出背包，模式切换等沿用 M3 关闭规则。节点换配方、全局重算、共享资源、MAX 改链警告详见交互补充第 3 节。

2026-09-15 补充（待实现）：隐藏筛选目标使用 FULL_ONLY，证据区分完整可行/充分排除完整/未知；排除完整不等于 BLOCKED，也不是部分计划。FULL_ONLY 和诊断是同一身份记录的能力层级，已充分失败可直接进入部分/缺口分析，不重跑完整阶段；预算/候选等截断不得作为充分失败。数量/约束/有效规则改变不复用不匹配证据。普通目录只留结论，当前悬停/详情最多两份有界方案。客户端本地绿状态只表示该授权快照下可行，绝非执行承诺；服务端仅能在新鲜身份核对后复用自己产生的充分失败。细则以 [M4.8/M4.9 设计](20-m4-filtering-and-client-planning.md) 3.5/6.3 为准。

### 7.2 缺口的诚实程度

缺口绑定当前选定路线：精确物品数量、Ingredient 的替代候选/标签、工作站、保护规则、解锁、容量、预算、世代变化分别显示。多种材料是“任选其一”，不把各替代分支缺口相加；共享钻石等资源要先做全局分配。

单根依赖的钻石缺口可精确；多路线困难场景只称“该方案还缺……”，不承诺全局最少基础材料。搜索被候选/深度/时间限制截断时明确标记不完备，不能自动部分执行。

### 7.3 载荷与确认边界

沿用一套服务端门面和序号屏障。M4 已新增/调整数量、诊断、详情与确认载荷，统一使用协议 6；联机双方不能混用协议 5 的旧版本。

被动预览仍最多 32 个根 ID，一次共享快照，条目只返回状态/简短原因。完整步骤、选定消耗、交付、缺口只在主动详情请求中返回且有条数/字节上限；不发送完整附近库存和容器坐标。缓存身份包括目标批次、完整/部分意图、节点配方约束、余料策略、详情修订号、配方/规则世代，不把 MAX 的结果当作 C 的一次结果。

确认请求携带服务端发给当前玩家的短期一次性令牌，不包含可写槽位计划。建议每玩家最多 1 个、200 tick 有效，绑定会话/菜单/目标/数量/策略/配方与规则世代及所见计划摘要。服务端只保存摘要与意图，不保存跨 tick 活容器句柄或长寿命执行计划。

确认时重新扫描和规划。若材料变体、消耗、步骤、产物、余量、缺口或部分/完整结果与玩家所见不一致，则不消耗，返回更新详情待再次确认。无关槽位变化不必机械拒绝；真正提交仍精确复验所用槽。令牌在尝试提交前消费，重复确认不重复执行；退出/死亡/换维度/换菜单/重载使之失效。普通 C 不自动网络重试。双击携带前一完整尝试的关联 ID，由服务端验证其真实结果和同会话身份；长按 repeat 不能生成部分意图。两次 C 不得因第一份成功耗尽材料而误触部分准备。

### 7.4 M4.8/M4.9 网络与确认修订（待实现）

计划协议 7，用有界、会话隔离的授权资源/容量值快照支持同核心客户端浏览；不发送容器坐标、活句柄、他人库存或未授权内容。版本按完整资源/容量/权限/规则比较，不等于扫描编号。旧协议 6 的批次、无资源同步和确认重搜索描述是当前实现，不是本次扩展后的协议要求。

M4.9 仅允许完整固定数量见证经服务端实际匹配/组装/剩余物、资源贡献、来源权限和容量重建后交原事务；其确认以新鲜验证替代重新找路线，摘要变化仍重确认。部分合成、双击失败关联仍由服务器证明；客户端 MAX 成功路线只证明可行下界。任何客户端产量、资源宣称、无解/最优断言都不能直接授权执行。完整契约及反重放/隐私/线程边界见补充设计与 ADR-0008，未实现前不改变实际操作语义。

## 8. 性能边界与实施门槛

下列是 M4.0 的起始测试参数，不是让玩家调大的性能开关：

| 约束 | 初始值/政策 |
|---|---|
| 固定/MAX 根批次上限 | 64；详情显示实际服务端上限 |
| 一次渐进 MAX 的计算分片 | 最多 32 份；耗尽后显示下界/未确定，不继续自动轮询 |
| 整链实际配方执行次数 | 128，包含中间步骤和根批次 |
| 依赖深度 | 12 |
| 展开状态 / 单需求候选 | 2048 / 16；截断必须标记未证明 |
| 主动规划时间 | 8 ms 软截止，检查每次展开及配方调用前后 |
| 被动预览 | 沿用整批 8 ms 软预算，单根递归子预算先测 1 ms；不是 32×8 ms |
| 全服主动/被动规划 | 同一 tick 合计 16 ms 软准入预算；公平限流，无无限队列 |
| 详情载荷 | 最多 128 步、32 个缺口，建议编码上限 64 KiB；不完整详情不得批准确认 |

数量达到上限不是资源缺失。超限计划不直接执行前缀；若已找到完整合法固定目标，可返回完整可行结果而不追求最优。未证明全量不可行时不能自动降级部分计划。MAX 的上限内最优性单独报告。

软截止不能抢占一次 Minecraft 调用；扫描、复制、提交及通知另行计时，不能用“求解 8 ms”掩盖整个 tick 卡顿。M4.0 必须测出单配方调用和完整事务尾延迟；若不能满足单 tick 安全，先降低有界批量/收窄支持范围，必要时另提主线程分片方案，不直接上异步世界访问或持久调度系统。

集中效率门禁设在 M4.4，先通过联合 MAX/可见页/详情计算的夹具基准，再在 M4.5 接入完整图页；不是等 UI 完成后才优化。普通单次查询、主动详情和 MAX 共用求解语义但使用不同优先级与预算，MAX 不可阻塞普通 C。详见交互补充第 4 节。

M3 连切分类约 2 秒收敛是待优化基线，不是 M4 可以放大的延迟额度。首先补只读开发测量：排队、往返、快照、求解、截断、刷新，区分预算不足与超时。相同目标耗尽预算后不得每 4 tick 无限重算；按现有缓存生命周期做有界退避，环境变化或主动操作可再尝试。

## 9. 验收判据

每项须有实现阶段的自动测试证据；GUI 与两机行为另做人测：

1. 上述八个数量示例全部通过，输入/输出/组件/剩余物逐项守恒；1 次木棍仍产 4 根。
2. 通用标签与精确材料竞争能够回溯；候选顺序和端点输入顺序固定时结果确定。
3. 有起始铁粒的合法转换成功；空资源环、深链、多分支和收益环有界终止、不免费产物。
4. 缺钻石单击零消费、双击可准备、长按不误触、重复准备不加工多余原木；NEVER 零变更；CONFIRM 无确认零变更；EXPLICIT_SAFE 只提交已证安全计划。
5. 严格/掉落两种容量策略、主产物必须装下、余料部分堆叠、空桶、实体创建失败/上限、受保护材料、锁/卸载、每一步配方锁定分别测试。
6. 两玩家/漏斗竞争、提取中途失败、输出失败、重复确认、模式/菜单变化、数据包重载：无复制/吞物，不执行旧计划。
7. 中间和最终步骤通知次数/输入与实际步骤对应，提交后事件异常不回滚物品，不阻断其余步骤通知。
8. 原版配方书筛选、轮播 C、未知/待确认与搜索限制、单次/多次缓存隔离、详情焦点/关闭、创造旁观隔离、不同缩放语言通过。
9. 测量完整服务端 tick 和请求阶段尾延迟；单/双玩家持续切页不形成无界队列、持续重建或卡顿。记录与 M3 同环境对照，不用平均耗时冒充最坏情况。
