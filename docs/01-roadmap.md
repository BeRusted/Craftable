# 实施路线图

## 1. 为什么重排原始两阶段

递归规划器如果没有“选择目标”的通用入口，就无法自然完成“鼠标指向钻石镐并直接制作”这一核心体验。Craftable 不再自行开发一套 JEI 风格主浏览器，而是把原版配方书前移为第一阶段核心前端：

1. **原版配方书增强**：复用搜索、图标、分页和分类，加入 3×3 环境语义、三态显示与 `C` 操作。进入第一阶段早期。
2. **统一计划解释**：原版配方书和 JEI 都展示会消耗什么、使用什么工作站、缺什么。与递归规划器同步完成。
3. **生态扩展**：第二阶段把更多模组配方、非标准动作和工作站 UI 接入原版配方书，同时完善 JEI 前端。

第一阶段专注纯原版体验，不让 JEI 或其他模组兼容反向支配核心架构。核心稳定后再在第二阶段接入 JEI；届时不会禁用、隐藏或降级原版配方书增强，两个前端始终调用同一服务端能力。

## 2. 阶段 0：可行性与契约原型

目标：先验证最危险的假设，不产出面向玩家的版本。

### M0.1 工程定名与基础清理（已完成）

- [x] 确定正式模组名、`mod_id`、Java 包名、许可证和初始版本策略；
- [x] 删除 MDK 示例注册内容并完成可构建初始化；
- [x] 建立 common/client/core 分层、网络骨架和测试源集；`compat` 目录推迟到确有兼容实现时创建；
- [x] 建立文档决策记录（ADR）目录，并记录原版配方书前端决策。

### M0.2 三个纯原版限时技术原型（已验收，2026-09-02）

1. **M0.2-A 原版配方书原型（部分通过，完成技术取证）**：悬停目标、有效 3×3 尺寸、`C` 请求和服务端状态显示均可注入；同时证实“额外描边”不会改变原版 `craftable` 集合与过滤，解锁集合不能承担 `ALL` 目录，伪装 3×3 尺寸也不能正确驱动 2×2 菜单虚影。
2. **M0.2-B 原版环境快照（核心路径通过）**：玩家实际验证箱子及其他原版存储容器材料均可被直接制作使用；锁、阻挡、战利品和竞争边界继续由 M1/M2 自动化覆盖。
3. **M0.2-C 直接合成事务（核心路径通过）**：服务端能从附近容器消耗材料并完成一次普通原版有序/无序合成；配方书显示异常不影响服务端权威执行。

验收结论：M0.2 作为“验证危险假设”的技术原型通过并关闭，但不能作为可发布功能通过。三个已确认缺口转为 M3 的强制验收项；详见 [M0.2 验收报告](07-m0.2-acceptance.md)。JEI 和第三方容器不阻塞 M0 或第一阶段核心开发。

## 3. 第一阶段：可信核心

### M1 基础协议与环境快照

- 服务端配置和客户端配置分离；
- 注册请求/预览/结果网络载荷；
- 玩家背包、个人末影库存和附近方块容器适配器；
- 半径扫描、已加载区块限制、双箱去重和稳定端点 ID；
- 工作台能力发现；
- 环境快照调试命令，仅管理员或开发环境可用。

验收：服务端能给出一致的资源清单与工作站清单，客户端不能伪造资源。

### M2 单步合成与补偿式事务

- 原版 2×2/3×3 有序、无序配方；
- 输入、输出、配方剩余物和组件匹配；
- 模拟 → 复验 → 提取托管 → 产出 → 插入 → 记录；
- 触发原版/NeoForge 的合成统计、进度与事件语义，不能只调用配方 `assemble`；
- 满背包、端点失效、资源竞争和回滚；
- 第一批 GameTest 与规划器单元测试。

验收：在专用服务器上连续和并发执行不复制、不吞物。

### M3 原版配方书增强

- 复用原版配方书的图标网格、搜索、分页、分类和多配方切换；
- 从客户端已同步的配方目录建立独立显示集合；`ALL` 不依赖原版解锁集合，也不修改玩家解锁进度；
- 按可见页批量取得同一环境世代的权威三态，把结果写入配方集合筛选语义，而不是在原版红框外追加另一层颜色；
- `showing craftable`、分类可见性、按钮样式、工具提示和 `C` 必须读取同一状态；
- 附近工作台时提供客户端与服务端一致的实体 3×3 背包网格，左键放置、虚影、结果槽和 Shift 点击都使用相同槽位拓扑；
- 工作台消失、玩家重生/切维度/切换游戏模式时安全刷新或关闭菜单，不替换 `Player` 的库存对象；
- `C` 键制作一个，另设“制作最大数量”操作；
- 可合成/部分可合成/不可合成三态及无障碍可区分样式；
- 简短但结构化的成功和失败反馈；
- 不通过批量解锁配方污染原版进度；`ALL/UNLOCKED_ONLY` 只控制显示策略。

验收：无 JEI 环境中，玩家不查命令也能完成钻石镐示例；材料分别位于背包与附近容器时，按钮状态、`showing craftable` 结果和 `C` 行为一致；左键预览在实体 3×3 中无错位。

### M4 递归规划与部分完成

- 配方超图、循环检测、记忆化和搜索预算；
- 多配方、多标签材料和来源优先级；
- 严格限制的中间产物准备；
- 缺失材料、工作站、权限和输出空间诊断；
- 计划预览面板。

验收：钻石不足时只制作目标所需的两根木棍，并显示精确钻石缺口；循环配方不会卡死服务器。

### M5 炉类处理

- 熔炉、高炉、烟熏炉配方；
- 按燃烧 tick 计算燃料与浪费；
- 剩余物、副产物和经验结算；
- 时间压缩开关、单次批量上限；
- 无可接受燃料时的明确诊断。

验收：铁矿、燃料、原木和相应工作站可端到端制作铁镐；关闭时间压缩后不静默绕过等待。

### M6 第一阶段收口

- 完成计划解释界面；
- 内置配置界面、键位冲突处理和本地化；
- 原版锁、可使用性和服务端权限策略收口；
- 性能基准、兼容测试、错误审计与迁移说明。

第一阶段发布目标：`0.4.0-beta`。版本号只是建议，定名时可调整。

## 4. 第二阶段：智能与扩展

### M7 安全撤销与历史

- `Z` 只撤销最后一笔仍可证明可逆的事务；
- 记录槽位变化、精确物品组件、输出位置、经验和端点版本；
- 任一相关状态已变化则拒绝撤销并解释原因；
- 初期只支持纯物品合成，随后再评估熔炼经验与世界交互。

### M8 智能路径与燃料优化

- 可逆配方识别和惩罚权重；
- 原料保留偏好、收藏/锁定材料和配方黑名单；
- 按请求批量联合优化燃料，而非逐件贪心；
- 向玩家展示选择该路径的原因。

### M9 高级环境检测

- `RADIUS`、`LINE_OF_SIGHT`、`REACHABLE` 三种模式；
- 主线程分时的有界可达性搜索；
- 方块变化、区块卸载、维度变化和玩家移动触发失效；
- 掉落物、运输矿车等实体资源端点；
- 拾取冷却、所有者、年龄和实体死亡竞态处理。

### M10 动作提供者

- 村民交易：职业、等级、库存、补货、折扣、声望和输入槽语义；
- 生物互动：剪羊等显式白名单动作；
- 每类动作独立定义前置条件、副作用、冷却、声音/统计和撤销能力；
- 默认不把任意右键交互自动转成“配方”。

### M11 生态兼容与配方书扩展

- 仅在核心体验稳定后验证 JEI 公共 API，并提供与原版配方书一致的 `C`/`Z`、三态和计划解释；原版增强始终保留；
- 发布稳定的工作站/动作适配器 API；
- 为高需求模组编写独立兼容模块；
- 将更多第三方配方类型、村民交易和显式生物互动映射为可展示的原版配方书条目或动作条目；
- 在背包界面加入或兼容更多工作站的必要 UI、状态和配方分类；
- 原版配方书和 JEI 均接入 `Z` 撤销、历史及一致的状态刷新；
- 纯原版配方书、原版配方书 + JEI 两种环境的功能对齐测试。

## 5. 每个里程碑的通用完成标准

- 功能只在服务端验证后事务化提交；
- 新语义有单元测试，涉及世界状态的行为有 GameTest；
- 专用服务器验证通过，不只测试集成客户端；
- 玩家可见文本有 `zh_cn` 和 `en_us` 本地化键；
- 调试日志不泄露其他玩家私有容器内容；
- 没有每 tick 全立方体扫描；
- 新兼容逻辑失败时降级为“不支持”，而不是猜测执行。

## 6. 后续产品决策点

- 是否以及何时选择首批领地/权限模组与工作站模组；这不是第一阶段核心的前置条件。

这些选择不会阻止先实现服务端规划核心，但会影响 UI 和公开兼容承诺。
