# 技术架构

M4 落地说明（2026-09-10）：下文 RecipeAction、完整 CraftPlan DAG、燃料/风险/适配器字段是跨阶段愿景，不是当前建类清单。当前唯一入口为 CraftingService，CraftSearch/ResourceLedger 求解并产生有序 CraftPlan，CraftingTransaction 一次提交；PlanView 仅是有界显示投影，CraftingSessions 仅保存短期意图/判据/摘要，不保存可执行计划。旧五个 DirectCrafting 类已移除。不得据未来字段提前建设通用动作框架。可选余料实体输出不授权扫描地面物品作为输入；详情页不新建服务端菜单，沿用 M3 网格/装备/光标生命周期。

## 1. 总体结构

M4.8d 第六批（2026-09-17，当前）：原协调器改为同一 2 ms/tick 截止点内最多 64 次连续派发，每次仍走 3:1 公平选择；普通目标创建搜索前应用同资源闭包，避免越过固定批次后的重复探索。没有第二队列/索引/状态表或线程；原发送器抽出四块轮转选择方法供八接收器测试。授权在动态结果库初始化后发布，时效与服务端事务安全边界不变。五轮会话、100 次返回、400 实际 tick 及规模静态构建单列测量；全量门禁和 M4.9 仍未完成。

M4.8d 第五批（2026-09-17）：ClientBrowsePlanner 同一前台槽承载详情、候选与 MAX；后台隐藏槽继续享有 3:1 配额，图投影也计为前台片。ClientRecipeStatusStore 从单配方键扩为规范化意图键，普通筛选/数量/约束共享同一结果库，部分意图不隔离完整证据；只在协调器保留最近一份显示计划。MAX 枚举有界数量、不另写数量求解器。显式确认先请求原服务端审阅，PlanView 的值身份不一致则停止并再次确认；本地结果无执行令牌。M4.9 未接入，完整性能门禁待收口。

M4.8d 第四批正式浏览（2026-09-16）：新增唯一 ClientBrowsePlanner 作为原值核心的客户端拥有者；Catalog、CraftSearch、ResourceLedger、MainInventoryInsertion 仍各一套算法，ClientRecipeStatusStore 是唯一目录结果库。CraftingDetailPayloads/CraftingWire 原位增加协议 7 的订阅、指纹、授权、分块与分片解码；原服务端准入覆盖捕获/编码，发送按玩家轮转。旧线上逐目标状态包/处理器退出，旧包和队列移至测试；不是生产双算。以下第一至第三批段落为历史实施边界。

M4.8d 第三批前置边界（2026-09-16）：原 Index 的同步与分片初始化共用 Builder；PlanningInput 内的 Catalog 按连接/运行时世代持有完整目录，PlanView 同样委托值输入。environment 仅增加约定的 BrowsingSnapshot 值类，CraftingSessions 原位承载只读捕获/稳定不透明源引用与独立授权时间，CraftingWire 原位承载有界值编码/分块接收。弱身份引用仅用于检测端点替换，不是可执行句柄；新鲜授权和唯一事务从未取消。这些前置边界已测试，但客户端生产拥有者、发送/握手/调度及 M4.9 未接入，协议仍 6；不增加第二索引、容量模拟器、状态库或执行服务。

M4.8c 第二批实施（2026-09-15，替代下方第一批的提取状态）：`PlanningInput` 是新增的唯一纯值配方边界，recipe/planner 顶层生产类由 9 个增至约定的 10 个。原 Index 冻结普通需求和默认余料；CraftSearch 不再持有 CraftingRecipes 服务端门面，服务器也通过同一值输入搜索。服务端门面只在搜索完成后对选定计划权威组装复验，随后仍交原事务。`run`/`advance` 共用一个显式阶段状态机；搜索进度与累计 CPU/状态额度分离，暂停不销毁 frontier/memo/闭包游标。没有接入客户端生产浏览、授权快照或客户端见证，也没有增加执行器、网络协议或线程池。

M4.8 第一批实施（2026-09-15）：原 `CraftingSessions` 的预览 LRU 已被同内容身份的 `PreviewState` 原位替代，跨批共享闭包与简短证据；容量模拟捕获值后仍调用同一实现。`CraftingRecipes.Index` 提供不依赖玩家的规范化入口，并把原候选查询逻辑移入同一 Index；客户端测试用真实同步数据调用它，但尚无客户端生产图实例/快照协议。实际匹配与组装仍是服务端专属，不能将当前对象称为可在线程间自由传递的纯模型。没有新增生产顶层类、第二求解器或第二事务；后续职责迁移/删除规则见 [M4.8/M4.9 设计](20-m4-filtering-and-client-planning.md)。

包只在所属里程碑确有实现时创建。当前与预留边界如下：

```text
org/berusted/craftable/
  api/            当前仅放内部稳定结果枚举，不承诺扩展 API
  environment/    原版扫描、资源端点、环境快照、短缓存和世代
  workstation/    原版工作站能力与稳定来源
  recipe/         普通原版配方索引、实际匹配/组装/剩余物验证
  planner/        有界搜索、账本、步骤计划、诊断和只读显示投影
  execution/      净容量模拟、唯一整链事务、短期交互会话（无撤销历史）
  network/        客户端请求和服务端结果载荷
  config/         服务端、通用和客户端配置
  client/         原版配方书增强、背包扩展、预览、键位
    recipebook/   原版配方书桥接、三态模型和窄范围客户端注入
  compat/...      第二阶段实际开始兼容时才创建
```

当前写操作调用方向仍为 `network -> execution/CraftingService -> planner + recipe + environment`；网络层不得绕过门面调用提交器。协议 7 的浏览与详情/候选/MAX 由客户端协调器以授权值调用同一 planner/recipe；核心不能引用客户端类，客户端不持有真实容器或执行权限。原服务端预览只用于显式审阅和本地不可用时有界单目标回退。第二阶段确有兼容实现前不发布扩展 API。

2026-09-13 验收修订不改变以上分层：候选可达性在原 CraftSearch 内纠正；配方卡片只消费客户端同步目录，节点沿用 PlanView。Overlay 复用原控件实例，一笔明确点击可等待当前 MAX 回复，换意图/关闭即取消；最终仍由服务端唯一确认及事务提交，不构造后台执行队列。顶部导航改为进度风格大图及底部操作条，不新建菜单或通用 UI 框架。

### 1.1 M4.7 配方知识增补（2026-09-12，已实现）

现有 `CraftingRecipes.Index` 已按配方世代共享 byId/byOutput 与规范化配方；新增知识直接附属于该索引：共享 Ingredient 需求及生产候选邻接，`CraftSearch` 和 `PlanView` 仍使用同一入口。不是另建配方注册表、持久 DAG 计划或图形执行器。

长期层只回答“哪些配方可以产生所需材料”，每次请求仍由 `ResourceLedger` 分配数量、来源、余量，检查当前工作站/解锁/容量，并由原事务复验提交。当前资源的可生产集合也属于临时层，不能混入静态图。相同需求被多个目标引用不会复制知识，也不会使一份材料可被重复消费。

新增一个窄职责 `RecipeKnowledgeCache` 负责存档内有界文件、校验和原子写入，不归入 `CraftingSessions`；游戏语义指纹与当前 Entry 的完整性验证仍由 Index 负责。文件仅保存可重建的 ID/关系；跨重启匹配当前权威配方及标签后重新绑定运行时对象。启动和实际数据重载执行指纹/读取，C 不做磁盘 I/O；写线程只接收不可变字符串快照。移动/库存变化保留知识，重载开启新世代并使旧会话失效；未知/损坏/超限回到原索引。正常停服释放索引并有界等待写入。本轮没有增加反向邻接、历史路线或协议字段。细则及体量预算调整见 [知识设计](19-m4-recipe-knowledge.md) 与 [ADR-0007](adr/0007-shared-recipe-knowledge.md)。

### 1.2 M4.8/M4.9 规划增补（2026-09-15，待实现）

依据 [客户端规划设计](20-m4-filtering-and-client-planning.md) 与 [ADR-0008](adr/0008-snapshot-scoped-client-planning.md)：从现搜索/容量层提取不可变目录、资源和规则输入，客户端浏览与服务端主动求解调用同一核心；服务端活端点、配方真实回调、授权与提交不进入客户端或工作线程。原 Index 的规范化规则只有一份，客户端只读实例不新建配方系统/磁盘缓存。

知识所有权分为：服务端权威数据、两端共用规范化/索引代码、两端各自按配方世代复用的运行时图、仅服务端磁盘缓存。默认客户端本地建图，先测一次构建成本；不因服务端“学过”就建设图同步。客户端关闭背包/换分类保留静态图，重连/配方世代变化才重绑；动态缓存关闭菜单时可释放，两种生命周期不能混淆。

按完整资源内容版本共享 Reachability、FULL_ONLY 证据和按需诊断；分类/搜索仅切换本地队列。原扫描编号不是库存版本。旧 32 ID 批次可作为短期迁移基线，最终不再承担常态隐藏全目录查询；不再额外建立服务端全目录推送求解器。使用原状态库与一次有限浏览会话，不建设持久任务服务。

来源引用在相同端点/槽复查时稳定，租期/扫描号不进入内容版本；未改变的复查只续期。先做同版本一次闭包复用，测量后才考虑原索引前向邻接替换，局部失效继续延后。完整证据与诊断为一条记录的阶段能力：充分失败跳过完整搜索，未知不可跳过；片额耗尽续同一进度，累计耗尽停止为未知，不保留新版五次被动重试。只有当前悬停/详情保留少量方案。

服务端新增最小授权值快照：精确可投入资源、必要主背包容量、权限/规则/配方世代，外部来源为会话引用而非坐标/槽写指令；不发送未授权或受保护的私密内容。只有经过完整校验的版本可用于本地显示，快照不预留物品。限时复查权限与内容，事件不能覆盖的库存变化用有界周期复查兜底。

完整固定数量见证可经 CraftingService 逐步用当前真实配方/来源/容量重建为 CraftPlan，再进入原 CraftingTransaction；无需为已验证路线重复搜索其他路线。客户端失败/部分/MAX 上界不是权威证明：部分合成及失败双击关联仍由服务器原求解裁定。摘要改变仍重确认，不变更一次性令牌、权限、主线程提交和补偿守恒。体量与网络上限见主设计；不得将下文历史版本的“不发资源/总是重搜索”绝对表述误用为禁止本次已规划的窄边界迁移。

## 2. 一次制作请求的数据流

```text
客户端从原版配方书选择目标
  -> M1 发送 {目标配方 ID, 请求序号}
  -> 服务端限流并验证玩家状态
  -> 构建当前环境快照
  -> M2 只接受普通原版有序/无序配方
  -> 构造真实 CraftingInput 并计算输出/剩余物
  -> 模拟玩家主背包的联合输出容量
  -> 复验每个来源槽的精确栈指纹与可用性
  -> 在服务器主线程提取托管并原子插入
  -> 提交后触发统计、判据、配方解锁与 NeoForge 事件
  -> 仅向请求玩家返回摘要
  -> 客户端展示产物、消耗或精确缺口
```

预览与执行是两次独立请求。当前执行必须重新规划；M4.9 完整见证路径可改为新鲜验证和重建。服务端自产、同身份且未过期的充分完整失败可以在新鲜资源比对后用于部分请求，避免重复完整阶段；不接受客户端失败声明。其余入口按需规划。所有路径均不能信任旧预览库存，玩家或漏斗可在两次操作之间改变箱子内容。

## 3. 核心数据契约

以下先描述 M1 已落地契约；后续字段只有进入对应里程碑后才能加入。

### `EnvironmentSnapshot`

- 维度、方块原点和一次性复制的扫描设置；
- 捕获游戏时间和按玩家单调递增的环境世代；
- 有序且 ID 唯一的 `ContainerEndpoint` 列表；
- 有序且 ID 唯一的 `WorkstationEndpoint` 列表；
- 活容器句柄只在服务器主线程短期存在，不持久化、不发往客户端。

### `ContainerEndpoint`（M1）

- 稳定 ID、所有权类型、可选位置、活 `Container` 与显式槽位区间；
- 玩家主背包只暴露 0..35，不含护甲和副手；
- `isStillValid` 用于缓存复用和提交前复验。

M2 已在这一边界上加入精确栈指纹、提交前复验和原版容器补偿语义，但没有扩展 `ContainerEndpoint` 或提前抽象第三方事务能力。

### `DirectCraftingPlan`（M2 历史契约，M4 已替换）

- 只描述一次普通原版工作台制作；
- 保存 2×2/3×3 完整输入网格、实际 `assemble` 输出、非空剩余物与逐来源槽提取意图；
- 所有 `ItemStack` 和集合在构造与读取边界防御性复制；
- 不包含递归步骤、燃料、批量、历史或第三方动作。

### `WorkstationCapability`

- M1 只定义 `CRAFTING_2X2` 与 `CRAFTING_3X3`；
- 每个来源具有唯一 ID 与可选方块位置；
- 炉类能力、批量、燃料和回滚等级进入对应里程碑后再扩展。

### `RecipeAction`

- 输入要求，可包含标签或精确组件；
- 输出、副产物和剩余物；
- 所需工作站能力；
- 资源和时间成本；
- 是否可批量、是否动态、是否可逆；
- 执行适配器和风险等级。

### `CraftPlan`

- 有序动作 DAG；
- 每个动作的次数和选定输入；
- 端点级提取/插入意图；
- 燃料与经验结算；
- 未满足要求；
- 计划成本、搜索预算使用量和诊断轨迹。

## 4. 环境发现

### 4.1 扫描触发

M1 只在以下时机扫描：

- 玩家请求预览且没有可复用的短缓存；
- 玩家请求制作，此时无条件重新扫描；
- 玩家跨方块、跨维度、重生、配置值变化、缓存超时或端点失效。

禁止每个 tick 遍历完整立方体。

### 4.2 扫描策略

1. 复制并验证服务端配置；
2. 枚举半径内位置，但跳过未加载区块；
3. 只接受 `minecraft` 方块和原版 `Container`；
4. 无副作用检查锁、物理阻挡、未生成战利品和 `stillValid`；
5. 规范化双箱并拒绝重复端点 ID；
6. 发现玩家 2×2 与工作台 3×3 能力；
7. 生成只在主线程短期使用的快照。

第三方能力、分 tick 扫描和精确权限提供者属于后续阶段，不进入 M1。

### 4.3 可达性

当前 M1/M2 明确使用有界方盒 `BOX` 扫描；欧式距离、视线与可达性均未提前实现。后续 `REACHABLE` 采用有界洪泛/BFS：

- 只在主线程读取世界碰撞状态，必要时分 tick；
- 寻找玩家可站立节点到工作站可交互面的路径；
- 有节点数、距离和时间上限；
- 搜索超限视为未知/不可用，不降级成无条件可用；
- 门、活板门、游泳、攀爬等特殊移动规则按迭代版本逐步加入。

## 5. 容器与权限

NeoForge 的 `IItemHandler` 是第三方物品存储兼容的首选接口，但它描述的是自动化可访问库存，不自动表示玩家有权使用。

访问判定采用提供者链：

1. 模组专用权限适配器；
2. 方块自身的锁、所有者和 `stillValid`/交互规则；
3. 领地或保护模组桥接；
4. 内建几何与距离规则；
5. 无法确定时按服务端策略允许或拒绝，公开服务器建议拒绝。

重要特例：

- 末影箱：附近方块授权访问当前玩家自己的 `PlayerEnderChestContainer`；
- 双箱：合并后只计数一次；
- 未生成战利品容器：不得仅为搜索结果而解包或泄露内容；
- 侧面库存：必须记录实际可提取的面，不能用 `null` 面绕过机器规则；
- 正在被其他菜单使用的容器：通常仍可像漏斗一样变化，因此提交前必须复验，而不是全局锁死菜单。

## 6. 工作站与第三方模组

Minecraft/NeoForge 没有“任意工作站执行任意配方”的统一能力。配方类型只描述匹配和产物，通常不完整描述机器能量、速度、催化剂、升级、副产物、污染、热量或所有权。

因此采用显式适配器：

```text
WorkstationAdapter
  supports(level, pos, player)
  capabilities(...)
  enumerateActions(recipeAccess, ...)
  simulate(action, context)
  commit(action, context)
  rollbackSupport()
```

原版工作台和炉类由内建适配器支持。第三方适配器应优先由对方模组或独立兼容模块提供。数据包可调整别名、黑名单和成本，不能安全表达复杂机器副作用时不得取代代码适配器。

## 7. 规划器边界

规划器是纯逻辑模块：输入不可变环境视图、规范化动作和目标，输出计划或诊断，不直接修改世界。

关键约束：

- 有界搜索，不追求无限配方图的全局最优；
- 同一物品的组件、损伤、附魔和配方匹配语义不得被简单 registry ID 抹平；
- 标签材料是候选集合，不在图构建时随意固定为第一项；
- 动态或特殊配方需要专用适配器，无法安全枚举的配方只支持玩家给出具体输入时执行；
- 数据包重载后失效运行时索引、预览及相关令牌；M4.7 磁盘知识须经新世代语义指纹验证后重新绑定，不沿用旧句柄或授权。

详细算法见 [规划与执行语义](03-planner-semantics.md)。

## 8. 补偿式事务

Minecraft 和通用 `IItemHandler` 没有跨多个库存的数据库事务，也没有统一锁或回滚接口。因此这里追求的是“服务端主线程内、先完整模拟、失败时守恒补偿”的应用层事务，而不是承诺所有第三方端点都能恢复到逐槽位完全相同的严格原子状态。只有显式适配器声明并验证了事务能力的端点，才能获得严格回滚等级。

### 8.1 提交协议

所有提交在服务端主线程执行：

1. 验证玩家仍在线、存活、同维度且未超出请求频率；
2. 重新计算端点指纹和权限；
3. 模拟全部提取、工作站动作与输出插入；
4. 按稳定顺序把输入提取到事务托管区；
5. 执行动作并计算输出；
6. 插入玩家背包或配置的输出端点；
7. 结算经验、统计和声音；
8. 写入事务日志并返回结果。

配方结果不能简单按次数乘法复制。每次或每个适配器声明的安全批次都要走规范化执行钩子，正确触发配方组装、剩余物、`onCraftedBy`、统计、进度/配方判据和 NeoForge 事件。通知类副作用放在物品提交成功之后，并隔离监听器异常，避免一个统计事件把已完成的物品事务撕裂。

### 8.2 失败策略

- 模拟失败：世界不变；
- M2 原版端点提取中途失败：从提交前逐槽备份恢复玩家主背包与所有受影响来源槽；
- 未来第三方端点若无法保证逐槽恢复，必须由适配器声明更弱的补偿等级，不能冒充 M2 的原版严格恢复；
- 输出容量不足：原则上在提取前失败；
- 第三方处理器在 `simulate` 阶段产生副作用：标记适配器不可信并禁用自动操作；
- 任何无法提供合理补偿的工作站动作，不能加入第一阶段自动事务。

Minecraft 主线程串行降低了并发复杂度，但漏斗、方块 tick、菜单点击和回调仍可能在相邻 tick 改变状态，因此“预览成功”从不等于“执行必定成功”。

## 9. 网络与安全

M1 客户端请求载荷严格只包含：

- 请求序号；
- 目标配方 ID。

M2 因新增 `RECIPE_LOCKED` 结果码把协议注册版本升级为 3。响应回显请求序号和结构化枚举；预览响应附服务端环境世代。请求序号只用于客户端丢弃过期显示，不参与服务端授权。

M3 当前协议为 **5**：预览请求改为最多 32 个 ID 的有界列表，响应共享一个环境世代并附有效扫描规则摘要；新增打开临时背包工作台的请求，仍只携带序号，服务端重新扫描授权。菜单内容使用原版菜单同步，不使用自建槽位包。旧协议不能混用。

服务端措施：

- 每玩家主线程限流并在退出时清理；
- 数量、字符串长度、资源 ID 和搜索预算上限；
- 忽略客户端提供的成本、来源和成功状态；
- 结果只同步给请求玩家，不广播附近容器内容；
- 网络处理切回服务端主线程后才访问世界。

## 10. 客户端前端：原版配方书与 JEI

第二阶段接入 JEI 时再评估统一 `CraftingFrontendBridge`；当前不为尚未实现的兼容注册接口。其预期职责为：

- 原版配方书适配器把当前悬停配方转换成目标，并保持原版搜索、分类、分页、提示和叙述行为；
- JEI 兼容层把 JEI 公共 API 提供的当前上下文转换成同一目标；
- 两个前端都把服务端预览映射为 `CRAFTABLE`、`PARTIAL`、`BLOCKED` 三种玩家可见状态；
- `C` 调用同一预览/执行命令，第二阶段的 `Z` 调用同一服务端撤销事务 ID；
- 提示和计划预览共用渲染模型；统一反馈路由按语义选择原版按钮/Tooltip、右上角 `SystemToast` 或可阅读面板，不允许各网络处理器自行选择 HUD 位置。

M2 对原版 `RecipeButton` 设定一条窄边界：按钮内部的定时图标轮播只是视觉表现，不能改变按钮的可制作状态或 `C` 键语义。客户端以该按钮当前展示集合中的候选配方为单位，按限流节奏补齐服务端状态，显示其中最佳状态，并优先把已确认可制作的候选作为执行目标。该规则不改写原版 `RecipeCollection` 的成员、解锁状态或 `showing craftable` 筛选；这些集合级增强仍属于 M3。

M3 已把 `RecipeCollection` 的已知/尺寸/可制作集合在背包活动期投影为统一服务端状态，离开时恢复原版；实际解锁记录不变。协调器优先查询可见候选，过滤模式额外轮询当前分类/搜索的隐藏候选。更新缓存但结果未变时不重建页面。目标选择独立于按钮动画索引，原版索引读取也校验当前列表。实体工作台也接入相同投影。生存/冒险是唯一允许模式；创造/旁观的菜单请求、预取、状态标记与 C 均关闭，服务端独立拒绝。切回生存不自动打开或升级背包。详细批次、重试与菜单契约以 ADR-0005 为准。

临时 `AmbientInventoryMenu` 继承原版 `CraftingMenu`，保留槽对象/ID并重新定位九宫格，末尾追加装备槽但使用原版背包装备坐标；对应屏幕复用 `CraftingScreen` 交互、原版 inventory.png 与 InventoryScreen 人物渲染，不再保留工作台样式侧栏。`Player.inventory`、`inventoryMenu` 和 M2 的事务实现不替换。工作台/距离/完整游戏模式/存活/维度失效后关闭，返还或掉落依原版生命周期处理。

原版配方书增强默认启用，且不会因为检测到 JEI 而自动关闭。JEI 兼容模块使用 `compileOnly` API 和运行时模组检测，核心不对 JEI 形成硬依赖。

NeoForge 1.21.1 的公开接口可以注册配方书分类和监听屏幕初始化、渲染及按键，但不能直接替换原版配方书的材料来源、有效网格和点击执行语义。因此客户端注入必须保持窄而可测试：优先使用公开 `ScreenEvent`，其次使用 Access Transformer 或 accessor Mixin 暴露“当前悬停配方”等只读状态；只有可合成判断和原版放置配方调用需要定点拦截。不得复制整份 `InventoryScreen` 或 `RecipeBookComponent`。

配方状态按当前环境快照世代缓存，只为当前可见条目和悬停目标请求预览；翻页、搜索、玩家移动或端点失效后按世代刷新。M3 必须在页面出现时主动预取可见按钮，悬停只提高目标优先级，不能成为首次获得状态的条件。状态生命周期中的 `UNKNOWN/PENDING/KNOWN` 与业务三态正交：制作后等待新预览时显示“待确认”，不得把尚未返回的状态伪装为 `BLOCKED`。禁止为全部配方逐帧发送网络请求。

## 11. 配置分层

- `SERVER`（M1 已实现）：水平/垂直范围、预览缓存 tick、末影箱入口；配置值是快照缓存身份的一部分。
- `COMMON`：M1 不注册，确有跨端非世界规则前保持为空。
- `CLIENT`（M1 已实现）：配方书增强开关和详细失败反馈；不能改变服务端结果。

M1.1 已通过 `IConfigScreenFactory` 接入 NeoForge 21.1.235 自带的 `ConfigurationScreen`。它复用 `OptionsSubScreen` 风格并直接消费现有 `ModConfigSpec`，因此不另建配置控件与持久化模型。

世界规则和客户端偏好必须在界面中保持分层：单人集成服务器允许编辑 `SERVER` 配置；连接远程服务器时，本地 `SERVER` TOML 不具权威性，M3 需要显示服务端同步的有效规则摘要。原版“选项”直达入口只能打开同一配置页；辅助功能页不得混入扫描、交易、掉落物或时间压缩等世界规则。详见 ADR-0003。

M3 已提供原版“选项”页直达按钮，其 Tooltip 展示最近一次服务端预览同步的有效规则（无快照时明确提示先打开背包），并增加客户端 `presentation.unlockedOnly` 显示选项。连接远程服务器或已开放局域网的世界中，沿用 NeoForge 配置页的服务端规则只读限制。
