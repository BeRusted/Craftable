# 技术架构

## 1. 总体结构

建议的 Java 包边界如下，名称可在正式定名后替换：

```text
org/berusted/craftable/
  api/            对外适配器接口和稳定数据契约
  environment/    扫描、可达性、权限、环境快照
  resource/       玩家/方块/实体资源端点
  workstation/    工作站能力与原版适配器
  recipe/         原版配方索引和规范化动作
  planner/        搜索、成本函数、部分计划、诊断
  execution/      模拟、事务提交、回滚、历史
  network/        客户端请求和服务端结果载荷
  config/         服务端、通用和客户端配置
  client/         背包扩展、浏览器、预览、键位
  compat/jei/     可选 JEI 集成
  compat/<modid>/ 独立第三方兼容模块
```

依赖方向必须单向：`client` 和 `compat` 可以依赖核心 API，核心规划器不能引用 JEI 或客户端类。

## 2. 一次制作请求的数据流

```text
客户端选择目标
  -> 发送 {目标配方/输出, 数量, 部分完成策略, 请求序号}
  -> 服务端限流并验证玩家状态
  -> 构建当前环境快照
  -> 规范化可用配方与动作
  -> 规划器生成完整计划或部分计划
  -> 所有端点执行无副作用模拟
  -> 复验环境指纹与权限
  -> 在服务器主线程提交事务
  -> 记录可审计结果/可撤销令牌
  -> 仅向请求玩家返回摘要
  -> 客户端展示产物、消耗或精确缺口
```

预览与执行是两次独立请求。执行时不能信任旧预览，必须重新规划；否则玩家或漏斗可在两次操作之间改变箱子内容。

## 3. 核心数据契约

以下是概念模型，不是最终 Java 签名。

### `EnvironmentSnapshot`

- 玩家、维度、游戏时间和配置世代；
- 有序 `ResourceEndpoint` 列表；
- `WorkstationCapability` 集合；
- 可用 `ActionProvider` 集合；
- 每个端点的稳定 ID、位置、访问面和状态指纹；
- 配方重载世代号。

### `ResourceEndpoint`

- `view()`：只读物品视图；
- `simulateExtract(request)`；
- `extractToEscrow(request)`；
- `simulateInsert(stacks)`；
- `insert(stacks)`；
- `fingerprint()`；
- `canPlayerUse(player, operation)`；
- `priority()`。

端点适配器负责遵守原对象的槽位限制、最大堆叠、侧面规则和失效规则。规划器不直接持有 `BlockEntity` 或 `IItemHandler`。

### `WorkstationCapability`

- 稳定能力 ID，例如 `minecraft:crafting_3x3`、`minecraft:smelting`；
- 来源位置与适配器 ID；
- 当前玩家是否可用；
- 可执行的动作类型；
- 批量、燃料、能量、升级等适配器约束；
- 提交和回滚能力等级。

### `RecipeAction`

- 输入要求，可包含标签或精确组件；
- 输出、副产物和剩余物；
- 所需工作站能力；
- 资源和时间成本；
- 是否可批量、是否动态、是否可逆；
- 执行适配器和风险等级。

### `CraftPlan`

- 有序动作 DAG；
- 每个动作的次数和选定输入；
- 端点级提取/插入意图；
- 燃料与经验结算；
- 未满足要求；
- 计划成本、搜索预算使用量和诊断轨迹。

## 4. 环境发现

### 4.1 扫描触发

第一阶段只在以下时机扫描：

- 打开背包或目标浏览器；
- 玩家请求预览/制作；
- 玩家移动超过阈值；
- 已知环境中的方块或能力失效；
- 配置、数据包或维度变化。

禁止每个 tick 遍历完整立方体。

### 4.2 扫描策略

1. 计算配置范围覆盖的已加载区块；
2. 枚举候选方块位置，受每 tick 预算限制；
3. 查询 `Capabilities.ItemHandler.BLOCK`，并尝试合法访问面；
4. 通过权限提供者链检查读取/提取/使用；
5. 通过方块和能力身份去重；
6. 发现工作站适配器；
7. 生成短生命周期快照并附状态指纹。

动态范围不适合为每个位置永久建立 `BlockCapabilityCache`。可只对当前快照热点建缓存，并在方块能力失效、区块卸载或玩家离开后释放。NeoForge 能力查询与失效机制是实现基础，但不能替代容器内容版本检测。

### 4.3 可达性

阶段一使用 `RADIUS` 或轻量 `LINE_OF_SIGHT`。阶段二的 `REACHABLE` 采用有界洪泛/BFS：

- 只在主线程读取世界碰撞状态，必要时分 tick；
- 寻找玩家可站立节点到工作站可交互面的路径；
- 有节点数、距离和时间上限；
- 搜索超限视为未知/不可用，不降级成无条件可用；
- 门、活板门、游泳、攀爬等特殊移动规则按迭代版本逐步加入。

## 5. 容器与权限

NeoForge 的 `IItemHandler` 是第三方物品存储兼容的首选接口，但它描述的是自动化可访问库存，不自动表示玩家有权使用。

访问判定采用提供者链：

1. 模组专用权限适配器；
2. 方块自身的锁、所有者和 `stillValid`/交互规则；
3. 领地或保护模组桥接；
4. 内建几何与距离规则；
5. 无法确定时按服务端策略允许或拒绝，公开服务器建议拒绝。

重要特例：

- 末影箱：附近方块授权访问当前玩家自己的 `PlayerEnderChestContainer`；
- 双箱：合并后只计数一次；
- 未生成战利品容器：不得仅为搜索结果而解包或泄露内容；
- 侧面库存：必须记录实际可提取的面，不能用 `null` 面绕过机器规则；
- 正在被其他菜单使用的容器：通常仍可像漏斗一样变化，因此提交前必须复验，而不是全局锁死菜单。

## 6. 工作站与第三方模组

Minecraft/NeoForge 没有“任意工作站执行任意配方”的统一能力。配方类型只描述匹配和产物，通常不完整描述机器能量、速度、催化剂、升级、副产物、污染、热量或所有权。

因此采用显式适配器：

```text
WorkstationAdapter
  supports(level, pos, player)
  capabilities(...)
  enumerateActions(recipeAccess, ...)
  simulate(action, context)
  commit(action, context)
  rollbackSupport()
```

原版工作台和炉类由内建适配器支持。第三方适配器应优先由对方模组或独立兼容模块提供。数据包可调整别名、黑名单和成本，不能安全表达复杂机器副作用时不得取代代码适配器。

## 7. 规划器边界

规划器是纯逻辑模块：输入不可变环境视图、规范化动作和目标，输出计划或诊断，不直接修改世界。

关键约束：

- 有界搜索，不追求无限配方图的全局最优；
- 同一物品的组件、损伤、附魔和配方匹配语义不得被简单 registry ID 抹平；
- 标签材料是候选集合，不在图构建时随意固定为第一项；
- 动态或特殊配方需要专用适配器，无法安全枚举的配方只支持玩家给出具体输入时执行；
- 数据包重载后丢弃索引、预览和撤销令牌。

详细算法见 [规划与执行语义](03-planner-semantics.md)。

## 8. 补偿式事务

Minecraft 和通用 `IItemHandler` 没有跨多个库存的数据库事务，也没有统一锁或回滚接口。因此这里追求的是“服务端主线程内、先完整模拟、失败时守恒补偿”的应用层事务，而不是承诺所有第三方端点都能恢复到逐槽位完全相同的严格原子状态。只有显式适配器声明并验证了事务能力的端点，才能获得严格回滚等级。

### 8.1 提交协议

所有提交在服务端主线程执行：

1. 验证玩家仍在线、存活、同维度且未超出请求频率；
2. 重新计算端点指纹和权限；
3. 模拟全部提取、工作站动作与输出插入；
4. 按稳定顺序把输入提取到事务托管区；
5. 执行动作并计算输出；
6. 插入玩家背包或配置的输出端点；
7. 结算经验、统计和声音；
8. 写入事务日志并返回结果。

配方结果不能简单按次数乘法复制。每次或每个适配器声明的安全批次都要走规范化执行钩子，正确触发配方组装、剩余物、`onCraftedBy`、统计、进度/配方判据和 NeoForge 事件。通知类副作用放在物品提交成功之后，并隔离监听器异常，避免一个统计事件把已完成的物品事务撕裂。

### 8.2 失败策略

- 模拟失败：世界不变；
- 提取中途失败：把托管物按逆序退回原端点；
- 原端点已拒绝退回：依次尝试玩家背包和受所有者保护的掉落，不得销毁；
- 输出容量不足：原则上在提取前失败；
- 第三方处理器在 `simulate` 阶段产生副作用：标记适配器不可信并禁用自动操作；
- 任何无法提供合理补偿的工作站动作，不能加入第一阶段自动事务。

Minecraft 主线程串行降低了并发复杂度，但漏斗、方块 tick、菜单点击和回调仍可能在相邻 tick 改变状态，因此“预览成功”从不等于“执行必定成功”。

## 9. 网络与安全

客户端请求载荷保持很小，只包含：

- 协议版本；
- 请求序号；
- 目标配方 ID 或可验证的输出描述；
- 请求数量；
- 部分执行策略；
- 可选预览令牌，仅用于提示过期而非授权执行。

服务端措施：

- 每玩家令牌桶限流；
- 数量、字符串长度、资源 ID 和搜索预算上限；
- 忽略客户端提供的成本、来源和成功状态；
- 结果只同步给请求玩家，不广播附近容器内容；
- 网络处理切回服务端主线程后才访问世界。

## 10. 客户端与 JEI

客户端有一个统一 `TargetSelectionController`：

- 内置浏览器把当前图标/配方转换成目标；
- JEI 兼容层把 JEI 公共 API 提供的当前上下文转换成同一目标；
- `C` 调用同一预览/执行命令；
- `Z` 调用服务端撤销事务 ID；
- 提示和计划预览共用渲染模型。

当 JEI 存在时，隐藏内置主浏览器，但保留 Craftable 独有的环境状态、计划解释和失败提示。兼容模块使用 `compileOnly` API 和运行时模组检测，核心不对 JEI 形成硬依赖。

## 11. 配置分层

- `SERVER`：范围、检测模式、时间压缩、部分执行、批量/搜索预算、权限策略、允许的动作；随世界保存并同步有效值。
- `COMMON`：服务器与客户端都必须一致但不属于世界规则的兼容选项，尽量少用。
- `CLIENT`：浏览器显示、键位、动画、提示详细度；不能改变服务端结果。

NeoForge 21.1.235 已包含配置界面支持，可基于 `ModConfigSpec` 提供接近原版风格的游戏内配置页。
