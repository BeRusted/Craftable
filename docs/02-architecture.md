# 技术架构

## 1. 总体结构

包只在所属里程碑确有实现时创建。当前与预留边界如下：

```text
org/berusted/craftable/
  api/            当前仅放内部稳定结果枚举，不承诺扩展 API
  environment/    原版扫描、资源端点、环境快照、短缓存和世代
  workstation/    原版工作站能力与稳定来源
  recipe/         原版配方索引和规范化动作（后续）
  planner/        搜索、成本函数、部分计划、诊断（后续）
  execution/      模拟、事务提交、回滚、历史
  network/        客户端请求和服务端结果载荷
  config/         服务端、通用和客户端配置
  client/         原版配方书增强、背包扩展、预览、键位
    recipebook/   原版配方书桥接、三态模型和窄范围客户端注入
  compat/...      第二阶段实际开始兼容时才创建
```

M1 的核心依赖方向为 `execution -> environment -> config/workstation`；`network` 只编排请求，`client` 只发送意图和展示结果。核心不能引用客户端类。第二阶段确有兼容实现前不发布扩展 API。

## 2. 一次制作请求的数据流

```text
客户端从原版配方书选择目标
  -> M1 发送 {目标配方 ID, 请求序号}
  -> 服务端限流并验证玩家状态
  -> 构建当前环境快照
  -> 规范化可用配方与动作
  -> 规划器生成完整计划或部分计划
  -> 所有端点执行无副作用模拟
  -> 复验环境指纹与权限
  -> 在服务器主线程提交事务
  -> 记录可审计结果/可撤销令牌
  -> 仅向请求玩家返回摘要
  -> 客户端展示产物、消耗或精确缺口
```

预览与执行是两次独立请求。执行时不能信任旧预览，必须重新规划；否则玩家或漏斗可在两次操作之间改变箱子内容。

## 3. 核心数据契约

以下先描述 M1 已落地契约；后续字段只有进入对应里程碑后才能加入。

### `EnvironmentSnapshot`

- 维度、方块原点和一次性复制的扫描设置；
- 捕获游戏时间和按玩家单调递增的环境世代；
- 有序且 ID 唯一的 `ContainerEndpoint` 列表；
- 有序且 ID 唯一的 `WorkstationEndpoint` 列表；
- 活容器句柄只在服务器主线程短期存在，不持久化、不发往客户端。

### `ContainerEndpoint`（M1）

- 稳定 ID、所有权类型、可选位置、活 `Container` 与显式槽位区间；
- 玩家主背包只暴露 0..35，不含护甲和副手；
- `isStillValid` 用于缓存复用和提交前复验。

M2 才在这一边界上加入模拟、托管、指纹和补偿语义；M1 不为了未来第三方能力提前抽象。

### `WorkstationCapability`

- M1 只定义 `CRAFTING_2X2` 与 `CRAFTING_3X3`；
- 每个来源具有唯一 ID 与可选方块位置；
- 炉类能力、批量、燃料和回滚等级进入对应里程碑后再扩展。

### `RecipeAction`

- 输入要求，可包含标签或精确组件；
- 输出、副产物和剩余物；
- 所需工作站能力；
- 资源和时间成本；
- 是否可批量、是否动态、是否可逆；
- 执行适配器和风险等级。

### `CraftPlan`

- 有序动作 DAG；
- 每个动作的次数和选定输入；
- 端点级提取/插入意图；
- 燃料与经验结算；
- 未满足要求；
- 计划成本、搜索预算使用量和诊断轨迹。

## 4. 环境发现

### 4.1 扫描触发

M1 只在以下时机扫描：

- 玩家请求预览且没有可复用的短缓存；
- 玩家请求制作，此时无条件重新扫描；
- 玩家跨方块、跨维度、重生、配置值变化、缓存超时或端点失效。

禁止每个 tick 遍历完整立方体。

### 4.2 扫描策略

1. 复制并验证服务端配置；
2. 枚举半径内位置，但跳过未加载区块；
3. 只接受 `minecraft` 方块和原版 `Container`；
4. 无副作用检查锁、物理阻挡、未生成战利品和 `stillValid`；
5. 规范化双箱并拒绝重复端点 ID；
6. 发现玩家 2×2 与工作台 3×3 能力；
7. 生成只在主线程短期使用的快照。

第三方能力、分 tick 扫描和精确权限提供者属于后续阶段，不进入 M1。

### 4.3 可达性

阶段一使用 `RADIUS` 或轻量 `LINE_OF_SIGHT`。阶段二的 `REACHABLE` 采用有界洪泛/BFS：

- 只在主线程读取世界碰撞状态，必要时分 tick；
- 寻找玩家可站立节点到工作站可交互面的路径；
- 有节点数、距离和时间上限；
- 搜索超限视为未知/不可用，不降级成无条件可用；
- 门、活板门、游泳、攀爬等特殊移动规则按迭代版本逐步加入。

## 5. 容器与权限

NeoForge 的 `IItemHandler` 是第三方物品存储兼容的首选接口，但它描述的是自动化可访问库存，不自动表示玩家有权使用。

访问判定采用提供者链：

1. 模组专用权限适配器；
2. 方块自身的锁、所有者和 `stillValid`/交互规则；
3. 领地或保护模组桥接；
4. 内建几何与距离规则；
5. 无法确定时按服务端策略允许或拒绝，公开服务器建议拒绝。

重要特例：

- 末影箱：附近方块授权访问当前玩家自己的 `PlayerEnderChestContainer`；
- 双箱：合并后只计数一次；
- 未生成战利品容器：不得仅为搜索结果而解包或泄露内容；
- 侧面库存：必须记录实际可提取的面，不能用 `null` 面绕过机器规则；
- 正在被其他菜单使用的容器：通常仍可像漏斗一样变化，因此提交前必须复验，而不是全局锁死菜单。

## 6. 工作站与第三方模组

Minecraft/NeoForge 没有“任意工作站执行任意配方”的统一能力。配方类型只描述匹配和产物，通常不完整描述机器能量、速度、催化剂、升级、副产物、污染、热量或所有权。

因此采用显式适配器：

```text
WorkstationAdapter
  supports(level, pos, player)
  capabilities(...)
  enumerateActions(recipeAccess, ...)
  simulate(action, context)
  commit(action, context)
  rollbackSupport()
```

原版工作台和炉类由内建适配器支持。第三方适配器应优先由对方模组或独立兼容模块提供。数据包可调整别名、黑名单和成本，不能安全表达复杂机器副作用时不得取代代码适配器。

## 7. 规划器边界

规划器是纯逻辑模块：输入不可变环境视图、规范化动作和目标，输出计划或诊断，不直接修改世界。

关键约束：

- 有界搜索，不追求无限配方图的全局最优；
- 同一物品的组件、损伤、附魔和配方匹配语义不得被简单 registry ID 抹平；
- 标签材料是候选集合，不在图构建时随意固定为第一项；
- 动态或特殊配方需要专用适配器，无法安全枚举的配方只支持玩家给出具体输入时执行；
- 数据包重载后丢弃索引、预览和撤销令牌。

详细算法见 [规划与执行语义](03-planner-semantics.md)。

## 8. 补偿式事务

Minecraft 和通用 `IItemHandler` 没有跨多个库存的数据库事务，也没有统一锁或回滚接口。因此这里追求的是“服务端主线程内、先完整模拟、失败时守恒补偿”的应用层事务，而不是承诺所有第三方端点都能恢复到逐槽位完全相同的严格原子状态。只有显式适配器声明并验证了事务能力的端点，才能获得严格回滚等级。

### 8.1 提交协议

所有提交在服务端主线程执行：

1. 验证玩家仍在线、存活、同维度且未超出请求频率；
2. 重新计算端点指纹和权限；
3. 模拟全部提取、工作站动作与输出插入；
4. 按稳定顺序把输入提取到事务托管区；
5. 执行动作并计算输出；
6. 插入玩家背包或配置的输出端点；
7. 结算经验、统计和声音；
8. 写入事务日志并返回结果。

配方结果不能简单按次数乘法复制。每次或每个适配器声明的安全批次都要走规范化执行钩子，正确触发配方组装、剩余物、`onCraftedBy`、统计、进度/配方判据和 NeoForge 事件。通知类副作用放在物品提交成功之后，并隔离监听器异常，避免一个统计事件把已完成的物品事务撕裂。

### 8.2 失败策略

- 模拟失败：世界不变；
- 提取中途失败：把托管物按逆序退回原端点；
- 原端点已拒绝退回：依次尝试玩家背包和受所有者保护的掉落，不得销毁；
- 输出容量不足：原则上在提取前失败；
- 第三方处理器在 `simulate` 阶段产生副作用：标记适配器不可信并禁用自动操作；
- 任何无法提供合理补偿的工作站动作，不能加入第一阶段自动事务。

Minecraft 主线程串行降低了并发复杂度，但漏斗、方块 tick、菜单点击和回调仍可能在相邻 tick 改变状态，因此“预览成功”从不等于“执行必定成功”。

## 9. 网络与安全

M1 客户端请求载荷严格只包含：

- 请求序号；
- 目标配方 ID。

协议注册版本为 2。响应回显请求序号和结构化枚举；预览响应附服务端环境世代。请求序号只用于客户端丢弃过期显示，不参与服务端授权。

服务端措施：

- 每玩家主线程限流并在退出时清理；
- 数量、字符串长度、资源 ID 和搜索预算上限；
- 忽略客户端提供的成本、来源和成功状态；
- 结果只同步给请求玩家，不广播附近容器内容；
- 网络处理切回服务端主线程后才访问世界。

## 10. 客户端前端：原版配方书与 JEI

客户端有一个统一 `CraftingFrontendBridge`，原版配方书和 JEI 都只是它的适配器：

- 原版配方书适配器把当前悬停配方转换成目标，并保持原版搜索、分类、分页、提示和叙述行为；
- JEI 兼容层把 JEI 公共 API 提供的当前上下文转换成同一目标；
- 两个前端都把服务端预览映射为 `CRAFTABLE`、`PARTIAL`、`BLOCKED` 三种玩家可见状态；
- `C` 调用同一预览/执行命令，第二阶段的 `Z` 调用同一服务端撤销事务 ID；
- 提示和计划预览共用渲染模型；统一反馈路由按语义选择原版按钮/Tooltip、右上角 `SystemToast` 或可阅读面板，不允许各网络处理器自行选择 HUD 位置。

原版配方书增强默认启用，且不会因为检测到 JEI 而自动关闭。JEI 兼容模块使用 `compileOnly` API 和运行时模组检测，核心不对 JEI 形成硬依赖。

NeoForge 1.21.1 的公开接口可以注册配方书分类和监听屏幕初始化、渲染及按键，但不能直接替换原版配方书的材料来源、有效网格和点击执行语义。因此客户端注入必须保持窄而可测试：优先使用公开 `ScreenEvent`，其次使用 Access Transformer 或 accessor Mixin 暴露“当前悬停配方”等只读状态；只有可合成判断和原版放置配方调用需要定点拦截。不得复制整份 `InventoryScreen` 或 `RecipeBookComponent`。

配方状态按当前环境快照世代缓存，只为当前可见条目和悬停目标请求预览；翻页、搜索、玩家移动或端点失效后按世代刷新。禁止为全部配方逐帧发送网络请求。

## 11. 配置分层

- `SERVER`（M1 已实现）：水平/垂直范围、预览缓存 tick、末影箱入口；配置值是快照缓存身份的一部分。
- `COMMON`：M1 不注册，确有跨端非世界规则前保持为空。
- `CLIENT`（M1 已实现）：配方书增强开关和详细失败反馈；不能改变服务端结果。

M1.1 已通过 `IConfigScreenFactory` 接入 NeoForge 21.1.235 自带的 `ConfigurationScreen`。它复用 `OptionsSubScreen` 风格并直接消费现有 `ModConfigSpec`，因此不另建配置控件与持久化模型。

世界规则和客户端偏好必须在界面中保持分层：单人集成服务器允许编辑 `SERVER` 配置；连接远程服务器时，本地 `SERVER` TOML 不具权威性，M3 需要显示服务端同步的有效规则摘要。原版“选项”直达入口只能打开同一配置页；辅助功能页不得混入扫描、交易、掉落物或时间压缩等世界规则。详见 ADR-0003。
