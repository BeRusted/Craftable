# 规划与执行语义

## 1. 为什么不是普通的配方递归

配方图不是简单的“一件输入变一件输出”树，而是带数量的有向超图：一个动作可同时消耗多个输入、产生多个输出，并要求特定工作站。标签材料、多配方、容器剩余物和可逆转换会形成分支与循环。

例如铁镐目标可能包含：

```text
铁镐
  <- 3 铁锭 + 2 木棍 @ 3x3 工作台
铁锭
  <- 铁矿 + 燃料 @ 熔炉
木棍
  <- 木板 @ 2x2/3x3 合成
木板
  <- 任意受支持的原木 @ 2x2/3x3 合成
```

规划器需要同时决定做哪些动作、做几次、每个标签选什么、从哪里取物、燃料用什么，以及失败时哪些中间产物值得真正制作。

## 2. 目标身份

优先使用“具体配方 + 请求次数”作为执行目标，而不是只使用输出物品 ID。原因是多个配方可能输出同一物品，动态配方的组件也可能不同。

当入口只能提供物品时：

1. 枚举所有可证明输出该物品的候选配方；
2. 用成本函数排序；
3. 在 UI 中允许切换并记住玩家偏好；
4. 服务端仍重新验证最终配方。

## 3. 规范化动作

每条配方先被转换为 `RecipeAction`：

- 输入为 `(IngredientConstraint, count)`；
- 输出为精确 `ItemStack` 或可计算函数；
- 剩余物单独列出，不能当作免费新产物；
- 工作站能力显式化；
- 经验、燃料、工具损耗和副产物显式化；
- 动态配方标记为“需要具体上下文”；
- 适配器声明可模拟、可批量、可回滚等级。

对于配方组件和数据，使用配方自己的匹配逻辑与 `ItemStack` 组件比较，不能只比较 `Item`。

特殊/动态配方（修复、染色、旗帜、地图复制等）通常无法仅从一个输出图标反推出合法输入。第一阶段将其分为：可枚举并有专用适配器、仅在玩家给出具体输入时可执行、完全不支持三类；不得把默认输出占位符展示成可直接递归制作的真实目标。

## 4. 搜索策略

建议采用“有界最佳优先搜索 + 需求向量记忆化”，而不是无条件深度优先递归。

### 4.1 状态

- 尚未满足的物品需求多重集；
- 已保留的现有资源；
- 已产生的中间产物和剩余物；
- 已使用工作站能力；
- 当前动作数、深度和成本；
- 路径中的物品/动作访问栈，用于循环检测。

### 4.2 词典序成本

完整计划按以下顺序选择：

1. 能否完成请求目标；
2. 缺失基础资源总量；
3. 是否使用被锁定或保留的物品；
4. 不可逆转换惩罚；
5. 燃料浪费；
6. 动作数量与配方深度；
7. 从较低优先级端点取物的成本；
8. 配方稳定 ID，保证相同环境得出确定结果。

不要把所有因素简单相加为一个易溢出或难解释的魔法分数。

### 4.3 有界性

必须同时限制：

- 最大递归深度；
- 展开状态数；
- 每个需求的候选配方数；
- 每次请求批量；
- 主线程规划时间；
- 单 tick 环境扫描预算。

超限返回 `SEARCH_BUDGET_EXCEEDED`，并附当前找到的最好诊断，不伪装成“材料不足”。

## 5. 循环与可逆配方

铁锭 ↔ 铁粒、方块 ↔ 锭等转换会形成循环。基础规则：

- 同一路径中再次出现不更小的等价需求状态时剪枝；
- 可逆边带轻微惩罚，避免无意义往返；
- 如果可逆转换能利用已有资源完成目标，仍应允许；
- 不通过正收益循环凭空创造资源；发现输入输出计量异常时禁用该循环并记录警告；
- 第二阶段可显式识别强连通分量，为常见 9:1/1:9 存储转换建立更高效模型。

## 6. 标签与替代材料

`Ingredient` 可匹配多种物品。选择候选材料时：

- 先使用玩家主动放入或偏好的物品；
- 再按资源端点优先级；
- 避免消耗有自定义名称、附魔、损伤或非默认组件的堆叠，除非配方明确需要；
- 避免为了满足一个通用标签去合成昂贵变体；
- 允许玩家配置保留/禁止消耗的物品与标签；
- 选择结果必须出现在预览中。

## 7. 部分完成

“缺材料时尽可能合成”必须是有界且面向目标的，否则一次失败可能把所有原木转换成玩家不想要的中间件。

### 7.1 最大有用前沿

完整目标不可达时，规划器寻找“最大有用前沿”：

1. 只制作某条当前候选目标路径确实需要的中间物；
2. 数量不超过完成当前请求批次的需求；
3. 优先制作可逆或低损失中间物；
4. 不消耗被锁定物品；
5. 不执行会产生世界副作用的动作；
6. 不制作与主要缺口下游无关的旁支产物；
7. 部分计划仍作为一个补偿式事务整体提交。

钻石镐缺少钻石时，可由一块木板制作正好两根木棍；不会把箱中所有原木清空。

### 7.2 交互模式

提供三种服务端允许、客户端偏好的模式：

- `NEVER`：目标不能完整完成就不修改世界；
- `CONFIRM`：显示部分计划，玩家再次确认后执行；
- `AUTO_SAFE`：自动执行满足上述安全规则的最大有用前沿。

默认采用 `AUTO_SAFE`，以符合“材料不足时尽可能完成”的核心体验；玩家客户端可要求每次确认，服务端也可把上限收紧为 `CONFIRM` 或 `NEVER`。

## 8. 炉类与燃料

### 8.1 计量

把每次炉处理统一为所需燃烧 tick。对一个批次联合选择燃料组合：

1. 总燃烧 tick 必须覆盖需求；
2. 最小化未使用燃烧 tick；
3. 再最小化稀有度/玩家保留成本；
4. 结算燃料容器剩余物；
5. 不使用规划器刚制作但明显更昂贵的燃料，除非没有其他路径。

第一阶段不持久化“虚拟余火”。如果燃料产生多余热量，该部分被视为浪费并在预览中显示。第二阶段可评估把余火绑定到具体炉方块，但这会引入持久状态和机器占用语义。

### 8.2 工作站类型

- 普通熔炉接受普通熔炼；
- 高炉只接受其实际匹配的配方；
- 烟熏炉同理；
- 营火没有燃料槽且有不同时间/并发语义，第一阶段不自动视为无等待熔炉；
- 第三方炉类只有适配器明确支持时可用。

### 8.3 经验

经验按实际执行的配方次数计算。实现前需用测试确认与原版小数经验取整/随机规则的一致性。

直接加经验点与生成经验球在经验修补、拾取事件和其他模组钩子上语义不同。第一阶段优先使用原版经验球授予路径并把这一副作用标记为暂不可撤销；若体验不佳，再通过 ADR 决定是否采用直接经验并公开差异。

## 9. 输出与副产物

默认输出顺序：

1. 最终目标进入玩家背包；
2. 中间产物只在后续动作需要时留在事务托管区；
3. 未消耗的中间物、配方剩余物和副产物进入玩家背包；
4. 若空间不足，整个事务在开始提取前失败；
5. 仅故障补偿时允许生成受保护掉落物，正常成功路径不把产物喷到地上。

所有输出都参与容量模拟，包括空桶、损坏工具、额外产物和不同组件导致的不可堆叠物品。

## 10. 失败诊断

服务端返回结构化代码和参数，客户端本地化。建议代码：

- `MISSING_RESOURCE(item/tag, count)`；
- `MISSING_WORKSTATION(capability)`；
- `RESOURCE_PRESENT_BUT_INACCESSIBLE(endpointType)`；
- `WORKSTATION_PRESENT_BUT_UNUSABLE(reason)`；
- `NO_SUPPORTED_RECIPE(target)`；
- `OUTPUT_FULL(requiredSlots)`；
- `SEARCH_BUDGET_EXCEEDED(bestKnown)`；
- `ENVIRONMENT_CHANGED`；
- `PERMISSION_DENIED`；
- `UNSAFE_ADAPTER(adapterId)`；
- `RATE_LIMITED`。

多个缺口按“最接近完成目标的候选计划”汇总，避免同时列出所有替代配方的海量材料。

## 11. 撤销语义

`Z` 不是倒放世界，也不是无条件返还。它是对最近事务执行一次经过验证的补偿事务。

### 11.1 可撤销条件

- 在服务端配置的短时间窗内；
- 玩家仍在同一维度和允许范围；
- 最终产物及组件仍能在记录位置或允许搜索范围内完整收回；
- 被触及端点的相关槽位没有发生不相关变化；
- 中间产物没有被继续使用；
- 没有不可逆世界副作用；
- 配方和配置世代未变化。

### 11.2 初始支持范围

先支持纯物品、纯合成事务。以下默认不可撤销：

- 已产生或拾取的经验球；
- 村民交易与声望变化；
- 生物互动、繁殖、剪毛；
- 掉落物实体已合并、消失或被他人拾取；
- 第三方工作站未声明可靠补偿；
- 玩家已消耗、放置、附魔或改变了产物组件。

撤销失败只提示原因，不做“尽可能返还”，避免半撤销造成新的困惑或漏洞。
